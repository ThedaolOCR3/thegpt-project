# RAG 탭 웹 문서 Neon 저장 구조 및 실제 적재 확인

- 작성일: 2026-09-01
- 문서 유형: 실행 흐름 및 데이터 구조
- 대상 기능: Admin RAG 탭(구 OCR 탭) VectorDB 저장
- 대상 저장소: Neon PostgreSQL `vector_db` Schema
- Embedding Provider: `jina-v4`, `medical-bgem3`
- 관련 보고서: `docs/2_reports/16_RPT_Jina_BGE_원격이중임베딩_RRF연동_20260831.md`

## 1. 문서 목적

Admin RAG 탭에서 웹페이지를 분석하고 `VectorDB에 저장` 버튼을 누르면 어떤
데이터가 Neon의 어느 테이블에 저장되는지 설명한다.

2026-09-01에 질병관리청 편두통 관련 웹페이지를 실제로 저장한 결과를 조회하여
다음 사항도 함께 확인했다.

- 원본 URL과 전체 추출 텍스트의 저장 위치
- Chunk 텍스트의 저장 위치와 개수
- Jina v4 및 Medical BGE-M3 Vector의 저장 위치
- 기존 Gemini용 `document_chunks.embedding` 컬럼의 사용 여부
- 논리 Vector 차원과 실제 pgvector 컬럼 폭의 차이

## 2. 결론

한 번의 웹 문서 저장은 세 테이블에 나뉘어 기록된다.

```text
vector_db.admin_documents 1행
└─ vector_db.document_chunks N행
   └─ vector_db.chunk_embeddings N × 2행
      ├─ jina-v4
      └─ medical-bgem3
```

이번 확인 사례에서는 다음과 같이 저장됐다.

```text
문서                       1개
Chunk                     37개
jina-v4 Embedding         37개
medical-bgem3 Embedding   37개
Embedding 합계            74개
```

## 3. 전체 저장 흐름

```text
Admin RAG 탭
→ 파일 또는 웹 URL 분석 Job 완료
→ 추출 텍스트를 Chunk로 분할
→ POST /api/admin/ocr/vector-save
→ 완료된 Job의 Chunk 조회
→ jina-v4 passage Embedding 생성
→ medical-bgem3 passage Embedding 생성
→ 두 Provider의 Vector 개수와 1024차원 검증
→ admin_documents INSERT
→ document_chunks INSERT
→ chunk_embeddings INSERT
→ 하나의 DB Transaction으로 COMMIT
```

Embedding이나 DB 저장 중 하나라도 실패하면 전체 Transaction을 Rollback한다.
문서만 저장되고 Chunk 또는 Vector가 누락된 부분 성공 상태를 만들지 않는다.

## 4. 테이블별 저장 내용

### 4.1 `vector_db.admin_documents`

웹 문서 한 건을 대표하는 상위 행이다.

| 컬럼 | 저장 내용 |
|---|---|
| `id` | 문서 UUID |
| `original_file_url` | 최종 웹페이지 URL |
| `ocr_extracted_text` | HTML 본문과 내부 이미지 OCR을 합친 전체 텍스트 |
| `ocr_status` | 정상 완료 시 `completed` |
| `uploaded_by` | 현재 저장 흐름에서는 `NULL` |
| `created_at` | DB 생성 시각 |

웹페이지 원본 HTML이나 다운로드한 이미지 파일은 이 테이블에 저장하지 않는다.
RAG 입력에 사용하는 최종 추출 텍스트와 출처 URL만 저장한다.

### 4.2 `vector_db.document_chunks`

`admin_documents.id`를 `document_id`로 참조하며, 분할된 텍스트 하나당 한 행을
저장한다.

| 컬럼 | 저장 내용 |
|---|---|
| `id` | Chunk UUID |
| `document_id` | 상위 문서 UUID |
| `chunk_index` | 문서 내 Chunk 순번, 0부터 시작 |
| `chunk_text` | 실제 검색 및 LLM Context에 사용할 텍스트 |
| `embedding` | 기존 Gemini용 `VECTOR(1024)` 컬럼, 새 저장 흐름에서는 `NULL` |
| `created_at` | DB 생성 시각 |

새 Jina/BGE 저장 기능은 `document_chunks.embedding`에 Vector를 기록하지 않는다.
이 컬럼은 기존 Gemini 파이프라인과의 호환을 위해 남아 있는 레거시 컬럼이다.

### 4.3 `vector_db.chunk_embeddings`

Chunk와 Embedding Provider의 관계를 저장한다. Chunk 하나에 Provider별로 한 행이
생기며 `(chunk_id, provider_name)` 조합은 Unique 제약을 갖는다.

| 컬럼 | 저장 내용 |
|---|---|
| `id` | Embedding 행 UUID |
| `chunk_id` | 대상 `document_chunks.id` |
| `provider_name` | `jina-v4` 또는 `medical-bgem3` |
| `dimension` | 모델이 반환한 논리 차원 `1024` |
| `embedding` | pgvector 검색용 Vector 배열 |
| `created_at` | DB 생성 시각 |

Chunk가 37개라면 다음 계산으로 74행이 저장된다.

```text
37 Chunk × 2 Provider = 74 Embedding
```

## 5. 1024차원 Vector를 `VECTOR(2048)`에 저장하는 이유

두 원격 모델은 각각 1024차원 Vector를 반환한다. 반면
`chunk_embeddings.embedding`의 물리 컬럼 폭은 여러 Provider를 수용할 수 있도록
`VECTOR(2048)`로 정의되어 있다.

저장할 때 1024개 실수 뒤에 1024개의 0을 추가한다.

```text
[1024차원 실제 Vector] + [0 × 1024] = VECTOR(2048)
```

`dimension` 컬럼에는 실제 모델 차원인 `1024`를 기록한다. 검색 Query Vector에도
동일한 0 Padding을 적용하므로 내적과 Norm에 0이 기여하며 코사인 유사도 결과는
변하지 않는다.

## 6. 실제 편두통 웹페이지 저장 결과

확인 대상은 저장 시점 기준 가장 최근의 HTTP 웹 문서다.

```text
document_id:
24fee86d-9d04-48e7-a06e-136039fd557d

original_file_url:
https://health.kdca.go.kr/healthinfo/biz/health/gnrlzHealthInfo/
gnrlzHealthInfo/gnrlzHealthInfoView.do?cntnts_sn=6557&utm_source=chatgpt.com
```

### 6.1 문서 행

```text
ocr_status      = completed
전체 텍스트 길이 = 14,600자
uploaded_by     = NULL
created_at      = 2026-09-01 07:09:19.082832+00:00
```

### 6.2 Chunk 행

```text
Chunk 개수   = 37
chunk_index = 0 ~ 36
Chunk 길이   = 약 317 ~ 508자
```

37개 Chunk의 `document_chunks.embedding` 값은 모두 `NULL`이었다. 따라서 이번
저장에는 Gemini Vector가 사용되지 않았다.

### 6.3 Provider별 Embedding 행

| Provider | 행 수 | `dimension` | 실제 저장 폭 |
|---|---:|---:|---:|
| `jina-v4` | 37 | 1024 | 2048 |
| `medical-bgem3` | 37 | 1024 | 2048 |
| 합계 | 74 | - | - |

## 7. 저장 전후 DB 건수 비교

이번 저장 직전에 확인한 상태는 다음과 같았다.

```text
admin_documents = 7
document_chunks = 36
chunk_embeddings = 0
```

저장 후 상태는 다음과 같다.

```text
admin_documents = 8
document_chunks = 73
chunk_embeddings = 74
```

증가량은 문서 1행, Chunk 37행, Embedding 74행으로 실제 저장 결과와 일치한다.

## 8. RAG 검색 시 사용되는 데이터

새 검색 흐름은 `document_chunks.embedding`을 조회하지 않는다.

```text
사용자 질문
→ jina-v4 query Vector 생성
→ medical-bgem3 query Vector 생성
→ chunk_embeddings.provider_name별 pgvector 검색
→ 두 검색 순위를 Chunk UUID 기준 RRF로 결합
→ 최종 document_chunks.chunk_text 반환
```

따라서 기존 문서에 `document_chunks`만 있고 `chunk_embeddings`가 없다면 새
Jina/BGE 검색 결과에는 나타나지 않는다. 기존 문서를 새 검색에 포함하려면 별도의
재임베딩 또는 재등록 작업이 필요하다.

## 10. 현재 확인된 주의사항

### 10.1 관리자 계정 기록

현재 `uploaded_by`는 `NULL`이다. 누가 등록한 문서인지 추적해야 한다면 인증된 관리자
ID를 저장 서비스까지 전달하는 후속 구현이 필요하다.

### 10.2 동일 URL 중복 등록

현재 저장은 URL 기준 Upsert가 아니라 항상 새 `admin_documents` 행을 생성한다. 동일
URL을 여러 번 저장하면 문서와 Chunk, Embedding이 중복 생성될 수 있다.

### 10.3 기존 문서 Backfill

이번 저장 전 존재하던 36개 Chunk에는 `chunk_embeddings`가 없었다. 기존 Gemini 또는
텍스트 전용 Chunk를 Jina/BGE 검색에 포함하려면 Backfill 정책을 별도로 협의해야 한다.

### 10.4 민감정보

`EMBEDDING_API_KEY`는 저장 데이터에 포함되지 않으며 Backend `.env`에서만 읽는다.
문서나 로그, Frontend 환경변수에 Key를 기록하지 않는다.
