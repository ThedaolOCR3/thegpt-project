# Codex 지시문 — MedGemma 2.0 생성 종료·반복·Role Leakage 설정 개선

## 1. 목적

현재 MediSense 웹서비스에서 최종 학습 모델인 **MedGemma 2.0**이 정상 답변을 마친 뒤에도 다음 내용을 추가 생성하는 현상을 개선한다.

- 동일하거나 유사한 문장 반복
- `환자:`, `의사:`, `사용자:`, `assistant:` 등의 가상 대화 생성
- 답변 완료 후 시스템 지침·라벨·코드·부가 텍스트 생성
- 종료 토큰을 만나지 못하고 출력 한도까지 계속 생성

이번 작업의 1차 목표는 파인튜닝이나 데이터셋 수정이 아니라, **Vast.ai 추론 서버에서 MedGemma 2.0에 적용되는 Chat Template, 종료 토큰, 생성 파라미터와 로그를 바로잡는 것**이다.

---

## 2. 실행 권한

이 문서는 구현 범위와 검증 기준을 정의하는 지시문이다.

- 담당자 또는 Codex는 사용자가 별도로 **코딩을 명시적으로 허가한 경우에만** 코드를 수정한다.
- 코딩 허가 없이 이 문서만 전달받았다면 정적 분석과 변경 계획까지만 수행한다.
- 코딩 허가를 받은 경우에도 이 문서에 지정된 파일과 MedGemma 2.0 범위를 넘어 임의로 리팩터링하지 않는다.

코딩을 허가받았다면 작업 전에 다음 문서를 읽고 준수한다.

- `docs/0_rule/01_백엔드공통규칙_BACKEND_CODING_GUIDE.md`
- `docs/0_rule/02_작업 완료 문서화 공통 지시서.md`

## 3. 대상 모델과 식별자

이번 변경 대상은 아래 모델 하나뿐이다.

| 구분 | 값 |
|---|---|
| Frontend/Backend 공개 모델 ID | `medgemma` |
| 화면 표시 이름 | `MedGemma 2.0` |
| Vast.ai 내부 모델 ID | `medgemma-final` |
| Base 모델 | `google/medgemma-4b-it` |
| Adapter | `gon-0130/medgemma-4b-lora-consultation-main-v2` |

다음 모델은 이번 변경 대상이 아니다.

- `medgemma-dataset` / MedGemma 1.0
- `gemma`
- `qwen`
- `llama`

다른 모델의 생성 결과와 설정이 바뀌지 않았음을 회귀검증해야 한다.

## 4. 현재 호출 경로

```text
Frontend 의료 상담
→ Backend MessageService
→ ai.consultation.consult()
→ LlmApplicationService
→ RemoteHttpLlmProvider
→ Vast.ai POST /v1/generate
→ scripts/vastai_medical_llm_server.py
→ medgemma-final Adapter
```

핵심 파일은 다음과 같다.

| 파일 | 역할 |
|---|---|
| `scripts/vastai_medical_llm_server.py` | 실제 tokenizer 로드, Chat Template 적용, `model.generate()` 실행 및 decode |
| `scripts/vastai_medical_llm_server.ipynb` | Vast.ai 모델 다운로드·서버 실행·수동 확인 |
| `backend/app/services/llm_runtime.py` | 공개 ID `medgemma`를 원격 `medgemma-final`에 매핑 |
| `ai/llm/providers/remote_http.py` | Backend에서 Vast.ai `/v1/generate` 호출 |
| `ai/consultation/pipeline.py` | 메인 상담이 원격 서버에 출력 토큰 수를 전달 |
| `ai/consultation/response_validator.py` | 생성 후 반복·역할 문자열·프롬프트 유출 제거 |

실제 생성 문제를 해결하는 1차 수정 위치는 `scripts/vastai_medical_llm_server.py`이다. Frontend 변경은 필요하지 않다.

## 5. 현재 상태

정적 분석에서 확인된 현재 설정은 다음과 같다.

| 항목 | 현재 상태 |
|---|---|
| Tokenizer | MedGemma Base tokenizer 사용 |
| Adapter Chat Template | `medgemma-final/chat_template.jinja`가 있으면 Base tokenizer에 덮어씀 |
| `apply_chat_template()` | `tokenize=False`, `add_generation_prompt=True` 사용 |
| EOS | `tokenizer.eos_token_id` 하나만 `model.generate()`에 전달 |
| `<end_of_turn>` | 존재 여부와 Token ID를 확인하지 않음 |
| `max_new_tokens` | 요청의 `max_output_tokens`를 그대로 사용 |
| 원격 API 기본 출력 | 256 tokens |
| 메인 상담 요청 | 512 tokens를 명시적으로 요청 |
| `repetition_penalty` | 1.12 |
| `no_repeat_ngram_size` | 미설정 |
| Decode | 입력 토큰 이후 새로 생성된 토큰만 decode |
| 생성 메타데이터 | `output_tokens`, `finish_reason` 반환 |
| 후처리 | 반복·가상 역할 문자열·프롬프트 유출 제거 기능이 이미 존재 |

현재 `finish_reason`은 생성된 토큰 수가 요청 한도에 도달했는지만 비교해 `length` 또는 `stop`으로 계산한다. 어떤 종료 토큰 때문에 멈췄는지는 구분하지 않는다.

## 6. 작업 범위

### 6.1 MedGemma 2.0 Tokenizer와 Chat Template 확인

Vast.ai에 실제 다운로드된 `medgemma-final`과 MedGemma Base 파일을 기준으로 다음 값을 확인한다.

- `tokenizer.__class__.__name__`
- `tokenizer.chat_template` 존재 여부와 실제 내용
- `tokenizer.eos_token`, `tokenizer.eos_token_id`
- `tokenizer.pad_token`, `tokenizer.pad_token_id`
- `tokenizer.unk_token_id`
- `tokenizer.all_special_tokens`
- `tokenizer.all_special_ids`
- `<end_of_turn>`의 Token ID
- 간단한 `system + user` 메시지에 `apply_chat_template(..., add_generation_prompt=True)`를 적용한 렌더링 결과

확인할 때 다음 조건을 지킨다.

1. `<end_of_turn>` 문자열이 실제 tokenizer vocabulary와 special token 목록에 있는지 확인한다.
2. `convert_tokens_to_ids("<end_of_turn>")` 결과가 `None` 또는 `unk_token_id`라면 종료 토큰으로 사용하지 않는다.
3. EOS와 EOT의 ID가 같다면 중복 없이 하나만 사용한다.
4. 실제 Chat Template이 assistant 생성 시작 위치와 각 메시지의 턴 종료 토큰을 올바르게 삽입하는지 확인한다.
5. API Key, 사용자 질문, 의료 문서 원문, 전체 답변은 로그에 남기지 않는다.

`add_generation_prompt=True`는 현재 정상 사용 중이므로 제거하지 않는다.

### 6.2 MedGemma 2.0 전용 종료 토큰 적용

`request.model == "medgemma-final"`인 경우에만 다음 원칙으로 종료 Token ID 목록을 구성한다.

```text
stop_token_ids = 중복 제거된 [tokenizer.eos_token_id, 유효한 end_of_turn_token_id]
```

그리고 MedGemma 2.0의 `model.generate()`에 해당 목록을 `eos_token_id`로 전달한다.

주의사항:

- `<end_of_turn>`이 실제 유효한 특수 토큰임을 확인하기 전에는 ID를 추정하거나 하드코딩하지 않는다.
- 다른 모델에 MedGemma 종료 토큰을 공통 적용하지 않는다.
- `pad_token_id`는 기존 정상 동작을 유지한다.
- 종료 토큰 목록은 정수 ID만 포함하고 `None`, `unk_token_id`, 중복 값을 제거한다.
- Transformers 버전에서 `eos_token_id` 목록 전달을 지원하는지 현재 고정 버전으로 확인한다.

### 6.3 MedGemma 2.0 전용 생성 파라미터

`medgemma-final` 요청에만 다음 목표값을 적용한다.

```text
max_new_tokens = 최대 256
repetition_penalty = 1.10
no_repeat_ngram_size = 4
```

기존 설정 중 다음 값은 우선 유지한다.

```text
do_sample = True
temperature = 0.7
top_p = 0.9
use_cache = True
remove_invalid_values = True
renormalize_logits = True
```

구현 시 요구사항:

1. 메인 상담 Backend가 현재 512를 요청하더라도 `medgemma-final`의 실제 `max_new_tokens`는 256을 넘지 않게 한다.
2. API 전체 스키마의 상한을 256으로 낮춰 다른 모델까지 제한하지 않는다.
3. `effective_max_new_tokens`처럼 실제 적용값을 별도로 계산하여 `finish_reason` 판정에도 같은 값을 사용한다.
4. `medgemma-dataset`, `gemma`, `qwen`, `llama`의 기존 생성 파라미터는 변경하지 않는다.
5. 256 tokens에서 정상 의료 답변이 문장 중간에 끊기는 회귀가 있는지 반드시 확인한다.
6. 종료 토큰을 정상 적용했는데도 256에서 유의미한 잘림이 반복된다면 임의로 512로 복원하지 말고, 320 또는 384 등의 대안과 측정 결과를 보고하여 승인을 받는다.

`repetition_penalty=1.10`과 `no_repeat_ngram_size=4`는 보조 수단이다. EOS/EOT와 Chat Template 확인보다 먼저 원인 해결로 간주하지 않는다.

### 6.4 새로 생성된 토큰만 Decode 유지

현재 다음 방식은 정상 구현이므로 유지한다.

```text
generated_ids = output sequence에서 input_tokens 이후 구간
answer = generated_ids만 decode
```

전체 `output`을 그대로 decode하여 입력 Prompt, System Prompt 또는 사용자 질문이 답변에 다시 포함되지 않게 한다.

### 6.5 종료 사유와 생성 토큰 로그 보강

MedGemma 2.0 요청에 대해 최소한 다음 진단 정보를 남긴다.

- 모델 ID: `medgemma-final`
- GPU 번호
- 입력 토큰 수
- 실제 생성 토큰 수
- 요청된 최대 출력 토큰 수
- 실제 적용된 최대 출력 토큰 수
- `finish_reason`
- 종료에 사용된 Token ID 또는 종료 유형(EOS/EOT/length/other)
- 생성 소요 시간

로그 정책:

- 기존 응답 필드 `output_tokens`, `total_tokens`, `finish_reason`과의 하위 호환성을 유지한다.
- `generated_tokens`라는 별도 이름을 도입한다면 `output_tokens`와 의미가 중복되지 않도록 계약을 명시한다. 가능하면 기존 `output_tokens`를 생성 토큰 수의 표준 필드로 유지한다.
- `finish_reason="length"`는 실제 적용된 256 tokens에 도달했을 때만 사용한다.
- 종료 Token ID로 멈췄다면 기존 외부 계약은 `finish_reason="stop"`으로 유지하되, 내부 로그에서 EOS와 EOT를 구분할 수 있게 한다.
- 사용자 질문, RAG Context, 전체 모델 답변, 인증 정보는 로그에 기록하지 않는다.

### 6.6 Role Leakage 후처리

`ai/consultation/response_validator.py`에는 이미 다음 후처리가 있다.

- 반복되는 꼬리 라인·인라인 패턴 제거
- 답변 자체 반복 제거
- `환자:`, `의사:`, `사용자:`, `user:`, `assistant:` 역할 문자열 제거
- System Prompt echo 제거
- JSON·라벨·특수 토큰 제거

따라서 1차 작업에서는 공용 후처리를 즉시 넓히지 않는다. 종료 토큰과 생성 설정을 먼저 반영하고 결과를 확인한다.

그래도 MedGemma 2.0에서 Role Leakage가 남으면 다음 조건을 만족하는 안전한 후처리안을 별도로 제안한다.

- 정상 답변 뒤에 새 대화 턴을 시작하는 명확한 역할 라벨부터 이후 텍스트만 제거
- `의사소통`, `사용자 경험`처럼 정상 문장에 들어가는 단어는 제거하지 않음
- 역할 라벨이 답변 중간에 등장하는 변형과 콜론의 전각 문자 `：`를 고려
- 다른 모델에도 적용되는 공용 함수 변경이므로 회귀 테스트를 먼저 추가
- 오탐 가능성이 있으면 구현 범위를 확대하지 말고 승인 요청

## 7. MedGemma 공유 구조 주의사항

현재 `medgemma-final`과 `medgemma-dataset`은 하나의 Base Model 객체와 tokenizer를 공유하고 Adapter만 전환한다.

따라서 다음을 주의한다.

1. `tokenizer` 객체 자체의 전역 설정을 변경하면 MedGemma 1.0에도 영향을 줄 수 있다.
2. 이번 생성 파라미터와 종료 ID는 가능한 한 `request.model == "medgemma-final"` 조건의 요청 단위 값으로 적용한다.
3. `medgemma-final/chat_template.jinja`와 `medgemma-dataset/chat_template.jinja`가 실제로 동일한지 비교해 결과를 보고한다.
4. 두 템플릿이 다르면 이번 작업에서 MedGemma 1.0까지 임의로 고치지 않는다. tokenizer 분리 필요성과 메모리·동시성 영향을 정리해 추가 승인을 요청한다.
5. Adapter 전환과 생성은 기존 GPU Lock 내부에서 유지한다.

## 8. 수정 허용 범위

사용자가 코딩을 명시적으로 허가한 경우 다음 파일만 우선 수정한다.

### 1차 허용

- `scripts/vastai_medical_llm_server.py`
- `scripts/vastai_medical_llm_server.ipynb`의 확인·Smoke Test 셀
- 관련 테스트 파일

### 조건부 허용

- `ai/consultation/response_validator.py`
- `tests/ai/consultation/test_response_validator.py`

조건부 파일은 서버 종료 설정 적용 후에도 Role Leakage가 재현되고, 공용 동작에 대한 회귀 테스트를 작성할 수 있을 때만 변경한다.

`ai/consultation/pipeline.py`의 공용 `DEFAULT_MAX_OUTPUT_TOKENS`를 바로 256으로 변경하지 않는다. 그 값을 바꾸면 MedGemma 2.0뿐 아니라 다른 모델의 메인 상담 요청도 함께 바뀌기 때문이다.

## 9. 제외 범위

이번 작업에서 다음은 하지 않는다.

- MedGemma 1.0 및 Gemma/Qwen/Llama 설정 변경
- 파인튜닝 또는 재학습 실행
- Adapter·Base Model weight 수정 또는 재업로드
- 학습 데이터셋 정제
- RAG, OCR, Embedding 변경
- Frontend UI 변경
- Database Schema 또는 Migration 변경
- API Key나 URL을 코드에 하드코딩
- 실제 의료 질문·답변 원문을 로그에 저장
- 무관한 리팩터링, 파일 이동, 이름 변경
- Git commit 또는 push

종료 설정을 정상화한 뒤에도 가상 대화가 정상 답변 본문 안에서 계속 생성된다면, 파인튜닝 데이터의 대화 포맷 또는 라벨 유출 문제로 분류하고 별도의 재학습 작업으로 보고한다.

## 10. 검증 절차

### 10.1 정적 검증

- `medgemma-final` 조건에만 새 생성 설정이 적용되는지 확인
- 다른 네 모델의 기존 설정이 유지되는지 확인
- EOS/EOT ID 목록에 `None`, `unk_token_id`, 중복 값이 없는지 확인
- 입력 이후 생성 토큰만 decode하는지 확인
- `finish_reason`이 요청값이 아니라 실제 적용 한도를 기준으로 계산되는지 확인
- 로그에 Prompt, 답변, API Key가 포함되지 않는지 확인

### 10.2 자동 테스트

최소한 다음 경우를 검증한다.

1. MedGemma 2.0의 유효한 EOS와 EOT가 중복 제거된 목록으로 생성기에 전달됨
2. `<end_of_turn>`이 없는 tokenizer에서는 EOS만 안전하게 사용됨
3. `<end_of_turn>`이 `unk_token_id`로 변환되면 종료 ID에서 제외됨
4. Backend가 512를 요청해도 MedGemma 2.0의 실제 상한은 256임
5. 다른 모델은 요청받은 기존 상한과 파라미터를 유지함
6. MedGemma 2.0에 `repetition_penalty=1.10` 적용
7. MedGemma 2.0에 `no_repeat_ngram_size=4` 적용
8. 새 토큰만 decode됨
9. 길이 종료와 EOS/EOT 종료가 올바르게 기록됨
10. 기존 Role Leakage 후처리 테스트가 계속 통과함

GPU가 없는 로컬 환경에서도 순수 Helper와 Mock tokenizer/model로 검증할 수 있도록 테스트 경계를 잡는다. 테스트를 위해 실제 모델 weight를 다운로드하지 않는다.

### 10.3 Vast.ai 수동 검증

코드 검증 후 실제 Vast.ai 서버에 반영하고 프로세스를 완전히 재시작한다. 기존 프로세스가 이전 코드를 계속 사용하지 않도록 PID와 시작 시각을 확인한다.

MedGemma 2.0에 대해 다음 유형을 포함한 질문으로 확인한다.

- 짧게 끝나는 일반 의료 정보 질문
- 설명과 주의사항이 필요한 중간 길이 질문
- 정보 부족으로 확인 질문이 필요한 증상 질문
- 기존에 반복 또는 가상 대화가 발생한 재현 질문
- 동일 질문 반복 호출

각 결과에서 다음을 기록한다.

| 항목 | 확인 내용 |
|---|---|
| 답변 완결성 | 256 tokens 안에서 문장이 자연스럽게 끝나는가 |
| 종료 사유 | EOS/EOT/length 중 무엇인가 |
| 반복 | 같은 문장·구절이 불필요하게 반복되는가 |
| Role Leakage | 가상 환자·의사·assistant 턴이 생성되는가 |
| Prompt Leakage | System Prompt 또는 입력 라벨이 노출되는가 |
| 안전성 | 기존 의료 안전 규칙을 유지하는가 |

실제 외부 검증은 사용자 또는 담당자의 Vast.ai 실행 권한과 API 사용 승인이 있을 때만 수행한다.

## 11. 완료 기준

다음 조건을 모두 만족해야 완료로 판단한다.

- MedGemma 2.0의 실제 Chat Template과 EOS/EOT 값이 확인됨
- `add_generation_prompt=True` 유지
- 유효한 EOS/EOT Token ID가 MedGemma 2.0 생성에만 적용됨
- 실제 최대 생성량이 우선 256 tokens로 제한됨
- `repetition_penalty=1.10` 적용
- `no_repeat_ngram_size=4` 적용
- 입력을 제외한 새 토큰만 decode됨
- `output_tokens`, `finish_reason`, 실제 종료 유형을 추적할 수 있음
- 기존 재현 질문에서 반복·가상 대화가 사라지거나 명확히 감소함
- 256 제한으로 인한 문장 중간 잘림 여부가 측정됨
- MedGemma 1.0, Gemma, Qwen, Llama의 설정이 변하지 않음
- 관련 자동 테스트 통과
- Vast.ai 재배포·재시작 필요사항이 문서화됨

종료 설정 이후에도 Role Leakage가 지속되면 이를 숨기지 말고 다음 중 어디에 해당하는지 분리해 보고한다.

```text
A. 종료 토큰 또는 Chat Template 문제
B. 생성 파라미터 문제
C. 공용 후처리 탐지 누락
D. 파인튜닝 데이터/Adapter 자체의 Role Leakage
```

`D`라면 이번 서버 설정 작업은 완료하되, 모델 재학습은 별도 작업으로 남긴다.
