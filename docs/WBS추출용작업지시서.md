현재 프로젝트 전체 코드와 docs 문서를 분석하여 **제출용 WBS(작업분할구조도)에 사용할 업무 항목​**을 정리해줘.

## 목적

이 WBS는 개발자가 내부적으로 사용하는 상세 일정표가 아니라 **교육 프로젝트 최종 제출용 문서**에 사용할 예정이다.

따라서 함수, 클래스, API Endpoint, 개별 컴포넌트 수준으로 너무 세분화하지 말고, 프로젝트에서 수행한 주요 업무가 한눈에 보이도록 정리한다.

## 분석 범위

현재 프로젝트의 다음 내용을 종합적으로 확인한다.

- Frontend
- Backend
- 관리자 페이지
- OCR
- 문서 Chunk 처리
- Embedding
- Neon / Vector DB
- RAG
- LLM 및 Fine-tuning
- Prompt Engineering
- LLM API / 서비스 연동
- 배포 및 실행 환경
- 테스트
- 프로젝트 문서

Git에 존재하는 코드뿐 아니라 `docs` 디렉터리의 작업 보고서가 있다면 함께 참고한다.

## WBS 작성 기준

대분류를 먼저 구성하고 각 대분류 아래에 **핵심 세부 업무를 최대 5개 정도만 작성**한다.

예:

1. 프로젝트 기획
2. 웹서비스 개발
3. OCR 및 문서 처리
4. RAG 시스템 구축
5. LLM 개발 및 평가
6. 서비스 통합 및 배포
7. 테스트
8. 문서 및 발표 준비

위 분류는 예시이며 실제 프로젝트 구현 내용을 분석해서 더 적절하게 수정해도 된다.

### 세분화 수준

다음처럼 너무 상세하게 작성하지 않는다.

- FastAPI 특정 Router 구현
- React 특정 Component 구현
- LoRA r 값 설정
- 특정 함수 수정
- 특정 Endpoint 추가

대신 다음 정도의 업무 단위를 사용한다.

- FastAPI Backend 구축
- 관리자 페이지 구현
- OCR 문서 처리 기능 구현
- Embedding 및 Vector DB 저장 구현
- RAG 검색 기능 구축
- LLM Fine-tuning
- 모델 성능 비교
- Prompt Engineering
- Frontend-Backend-AI 서비스 통합

## 일정 분석

가능하면 프로젝트 내 문서와 코드 변경 내용을 참고하여 각 업무가 실제로 진행된 순서를 추정한다.

정확한 날짜를 확인할 수 없는 경우 억지로 날짜를 만들지 말고,

- 선행 작업
- 병렬 진행 가능 작업
- 후행 작업

관계를 중심으로 정리한다.

특히 이 프로젝트는 웹 개발, OCR/RAG 개발, LLM 개발이 일부 기간 동안 병렬로 진행되었으므로 이를 고려한다.

## 작업자

작업자 또는 담당자 항목은 **작성하지 않거나 빈칸으로 둔다.**

현재 목적은 업무 구조와 일정 정리이며 담당자 배정은 나중에 별도로 한다.

## 출력 형식

먼저 아래 형식의 표로 작성한다.

| WBS | 주요 업무 | 세부 업무 | 예상 진행 순서/기간 | 근거 |
|---|---|---|---|---|
| 1 | 프로젝트 기획 | ... | ... | 관련 코드/문서 |
| 1.1 |  | ... | ... | ... |

그 다음 아래 내용을 간단하게 정리한다.

### 1. 추천 대분류
최종 제출용으로 사용할 대분류 목록

### 2. 병합해도 되는 업무
제출용 WBS에서는 굳이 별도 항목으로 나누지 않아도 되는 업무

### 3. 반드시 별도로 표시할 업무
프로젝트의 핵심 기술 또는 주요 결과물이므로 WBS에 표시하는 것이 좋은 업무

### 4. 전체 개발 흐름
프로젝트 진행 흐름을 한 줄 형태로 정리

예:
기획 → 웹 기반 구축 / LLM 개발 / OCR 개발 → RAG 구축 → 서비스 통합 → 테스트 → 문서화

## 중요

이번 작업에서는 Excel이나 Markdown 파일을 새로 생성하지 않는다.

먼저 **WBS에 어떤 항목을 넣을 것인지 분석 결과만 출력**한다.
