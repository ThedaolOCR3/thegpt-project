# 프로젝트 전체 구조 및 실행 흐름 분석

> 분석 기준일: 2026-09-04  
> 분석 방식: 코드·설정·마이그레이션·테스트의 읽기 전용 정적 분석  
> 변경 범위: 본 보고서 신규 작성만 수행. 기존 코드·설정·DB·외부 API는 변경하거나 실행하지 않음.  
> 판정 표기: `확인됨`, `추정`, `미확인`, `미구현`, `Mock`, `사용되지 않는 것으로 보임`

## 1. 프로젝트 개요

### 1.1 한 줄 설명

MediSense는 문서·웹페이지 OCR, Jina v4와 Medical BGE-M3 이중 임베딩 기반 의료 RAG, 원격 파인튜닝 LLM을 결합한 React/FastAPI 의료 상담 웹 서비스다.

### 1.2 실제 기술 스택

| 영역 | 확인된 기술 |
|---|---|
| Frontend | React 19, TypeScript, React Router 7, Vite 8, Tailwind CSS 4 |
| Backend | FastAPI, Python 3.11 이상(로컬 안내는 3.12), Pydantic, SQLAlchemy 2 |
| Database | Neon PostgreSQL, `app_db`/`vector_db` 스키마, pgvector |
| OCR | PaddleOCR 3.7/PP-OCRv5, PyMuPDF, Pillow, OpenCV, python-docx, python-pptx |
| RAG | 문자 기반 청킹, Jina v4 + Medical BGE-M3, pgvector cosine search, RRF, 선택적 reranker |
| LLM | Vast.ai 원격 FastAPI 서버, Gemma/MedGemma/Qwen/Llama LoRA·QLoRA 5개 런타임 항목 |
| 인증 | JWT Bearer, 이메일 인증, Google/GitHub OAuth 코드 흐름, 게스트 계정 |
| Storage | Cloudflare R2(S3 호환), 관리자 대용량 업로드와 프로필 이미지 |
| 배포 | Backend Cloud Build → Artifact Registry → Cloud Run, Frontend Cloudflare Workers 정적 assets 설정 |

### 1.3 핵심 결론

- `확인됨`: 메인 상담은 `POST /api/conversations/{id}/messages`에서 시작해 RAG와 공통 원격 LLM 런타임까지 실제 코드로 연결된다.
- `확인됨`: Admin OCR과 `/api/documents/ocr`은 같은 `ai.ocr.analyze_document()` 코어를 사용한다.
- `확인됨`: Admin LLM은 Mock이 아니라 `RemoteHttpLlmProvider`를 통해 원격 모델을 호출한다. 다만 원격 서버의 현재 생존 여부는 외부 API 호출 금지에 따라 `미확인`이다.
- `부분 구현`: 채팅 첨부파일은 검증 후 메타데이터만 저장한다. 파일 본문은 상담 프롬프트나 RAG에 들어가지 않는다.
- `미구현`: `/document`, `/ocr` 사용자 화면은 제목만 출력하는 placeholder다.
- `Critical`: 다수의 `/api/admin/*` API에 Backend `require_admin`이 없다.
- `High`: OCR Job이 프로세스 메모리와 `asyncio.create_task()`에만 존재해 Cloud Run 재시작·스케일아웃·응답 후 CPU 제한에 취약하다.
- `High`: ORM `ChunkEmbeddings.embedding`은 `VECTOR(2048)`인데 최신 마이그레이션과 Repository는 `VECTOR(1024)`를 전제로 한다.

### 4.3 API 호출 구조

```text
Feature / Hook
→ src/api/* 또는 features/*/*Api.ts
→ services/apiClient.ts
→ `${VITE_API_URL 또는 http://localhost:8000/api}${path}`
→ FastAPI
```

- 공통 Client는 JSON과 FormData를 구분하고 Bearer token을 선택적으로 붙인다.
- 상담·대화·검색은 `withChatToken()`을 통해 로그인 token 또는 자동 발급 게스트 token을 쓴다.
- 프로필 이미지는 공통 Client 대신 자체 `API_URL + fetch` 구현을 쓴다. API 주소·오류 처리 중복 가능성이 있다.
- `vite.config.ts` proxy는 `/api/v1`만 대상으로 하지만 실제 기본 Client prefix는 `/api`다. 현재 Client가 절대 `localhost` URL을 쓰므로 로컬 기본 동작에는 proxy가 개입하지 않는다.

## 5. Backend 구조

### 5.1 진입점

핵심 진입점은 `backend/app/main.py`의 `create_app()`과 모듈 전역 `app`이다.

```text
uvicorn app.main:app
→ create_app()
→ CORS
→ app.api.router.api_router를 settings.api_prefix(`/api`)에 mount
→ OAuth callback Router를 root에 mount
→ upload 예외 handler 등록
→ /health, /health/db
```

`APP_ENV=local`이면 Git에 포함되지 않을 수 있는 `backend/local_lab` Router를 선택적으로 import한다.

### 5.2 계층 관계

```text
Router: HTTP 입력, 인증 의존성, 예외→상태코드 변환
  ↓
Service: 업무 흐름, AI 코어 호출, 트랜잭션 조율
  ↓
Repository: SQLAlchemy 조회·저장
  ↓
Neon PostgreSQL

Service → ai/*: OCR, RAG, LLM, 상담, 평가의 Framework 독립 로직
```

실제 코드는 전반적으로 이 계층을 지키지만 일부 Router가 Service 함수를 바로 호출하고, ORM은 `models/generated.py` 한 파일에 집중돼 있다.

```text
→ MessageRepository.create(assistant message)
→ ConsultationLogRepository.create()
→ Frontend MessageBubble
```

### 7.2 예외·Fallback

- RAG 검색 실패 시 DB rollback 후 빈 context로 LLM 상담을 계속한다.
- 응급 키워드가 잡히면 LLM을 호출하지 않고 119/응급실 고정 응답을 반환한다.
- LLM 실패 시 `FALLBACK_ANSWER`를 반환하고 `is_fallback`, `error_type`을 상담 로그에 남긴다.
- 응답 검증은 특수 token, Markdown, 반복 문장, 위험한 약물 용량 패턴 등을 후처리한다.
- 이 안전 로직은 공학적 규칙 기반이며 의료진 검증 완료 증거는 코드에서 확인되지 않는다.

### 7.3 채팅 첨부파일의 실제 상태

`POST .../messages/upload`는 파일 수·확장자·크기만 확인한다. 원본 byte는 요청 종료 후 버리고 `pending-upload://...` URL과 메타데이터만 DB에 저장한다. 질문 text가 있으면 파일 내용과 무관하게 text만으로 RAG/LLM을 실행한다. 첨부만 있으면 안내 문구를 반환한다.

방금 선택한 이미지의 OCR은 사용자가 미리보기 패널을 열 때 별도로 `/api/documents/ocr`을 호출해 브라우저 화면에만 표시한다. 수정한 OCR text도 상담이나 DB에 반영되지 않는다.

## 8. OCR 구조

### 8.1 공통 OCR 코어

```text
UploadFile
→ backend/app/services/ocr_workflow.py
→ ai.ocr.OcrDocumentInput + OcrProcessingConfig
→ ai/ocr/validation.py
→ ai/ocr/pipeline.analyze_document()
   ├─ PDF: native text / scanned page / hybrid image block
   ├─ PNG/JPG: preprocess → PaddleOcrService
   ├─ DOCX/PPTX: 직접 XML/라이브러리 추출 + 포함 이미지 OCR
   ├─ JSON/JSONL/CSV/TXT: 인코딩·형식 검증 후 직접 추출
   └─ ZIP: 지원 내부 문서 순회·통합
→ postprocessing
→ OcrDocumentResult
```

Paddle 모델은 지연 초기화하고 동일 설정 인스턴스를 cache하며 추론은 lock으로 직렬화한다. Backend Adapter는 CPU OCR을 `asyncio.to_thread()`로 넘긴다.

### 8.2 구현 개수와 중복 판정

| 경로 | 사용 위치 | 코어 공유 | 차이 |
|---|---|---|---|
| `ocr_workflow.analyze_upload` | `/api/documents/ocr` | `ai.ocr.analyze_document` | OCR 결과만 즉시 반환 |
| `ocr_workflow.process_document` | Admin 20MB 이하 파일 | 동일 | OCR 후 Admin 문자 Chunk/품질 상태 추가 |
| `web_ocr_workflow.process_url` | Admin URL | `ai.ocr`의 web extractor와 Paddle engine | SSRF 방어 fetch, HTML 본문+내부 이미지 OCR |
| `large_document_service.process` | Admin 20MB 초과 | 일부 | R2 streaming text/ZIP, chunk artifact; 작은 ZIP binary member만 공통 OCR |
| `services/hybrid_ocr/__init__.py` | 호환 import | `ocr_workflow.process_document` 재-export | 별도 구현 아님 |

따라서 핵심 OCR 엔진은 한 개다. 파일·웹·대용량 입력 Adapter가 세 갈래이며, 과거 `hybrid_ocr`는 중복 구현이 아니라 호환 별칭이다.

### 8.3 Admin OCR 흐름

```text
OcrPanel → useOcrTest → apiAdminAiService
  ├─ 파일 ≤20MB: POST /admin/ocr/jobs
  ├─ URL: POST /admin/ocr/url-jobs
  └─ 파일 >20MB: R2 multipart 4단계 → POST /admin/ocr/jobs/remote
→ GET /admin/ocr/jobs/{jobId} 700ms polling
→ 추출 text/chunks/readiness 검토
→ 수동 POST /admin/ocr/vector-save
→ Jina/BGE passage embedding 병렬 생성
→ AdminDocuments + DocumentChunks + ChunkEmbeddings 저장
```

OCR engine을 사용자가 선택하는 UI는 없다. 형식과 PDF 구조에 따라 직접 추출/PaddleOCR을 자동 선택한다.

## 9. RAG 구조

### 9.1 입력·저장 파이프라인

```text
관리자 파일/URL 또는 scripts/rag_ingest.py 데이터셋
→ text 정제
→ chunking
→ Jina v4 passage embedding (1024)
→ Medical BGE-M3 passage embedding (1024)
→ vector_db.admin_documents
→ vector_db.document_chunks
→ vector_db.chunk_embeddings(provider별 1행)
```

데이터셋 Adapter는 `asan`, `snuh-clinical-qa`, `health-search-qa`, `ai-healthcare-qa`, `komed-instruct`, `genmed-gpt`, `kdca-openapi` 7개다. 대량 적재는 `rag_bulk_ingestion_service`가 batch embedding과 batch commit을 수행한다.

### 9.2 질문 검색·생성 파이프라인

```text
질문
→ 진료과 키워드 분류
→ Jina query vector → provider별 cosine Top-20 이상
→ BGE query vector  → provider별 cosine Top-20 이상
→ RRF(k=60)
→ source_tier 및 진료과 soft boost
→ Top-5
→ 각 chunk 최대 800자, 최대 5개 Prompt 삽입
→ 선택 LLM
```

| 단계 | 상태 | 관련 파일 |
|---|---|---|
| OCR/문서 입력 | 구현 | `ocr_workflow.py`, `web_ocr_workflow.py`, ingestion adapters |
| 정제 | 구현 | `ai/ocr/postprocessing.py`, `ai/rag/ingestion/cleaning.py` |
| Chunking | 구현 | `ocr_chunk_service.py`, `ai/rag/chunking.py` |
| 이중 Embedding | 구현·외부 의존 | `core/rag_embedding.py`, `embeddings/remote.py` |
| Vector 저장 | 구현 | `admin_ocr.py`, `document_repository.py`, bulk ingestion |
| Similarity search | 구현 | `document_chunk.py` |
| RRF | 구현 | `rag_search_service.py`, `ai/rag/hybrid.py` |
| Reranker | 선택 구현 | `ai/rag/reranker.py`; 메인 상담 기본값은 꺼짐 |
| Prompt context | 구현 | `ai/consultation/context.py` |
| 상담 LLM 연결 | 구현·원격 상태 미확인 | `message.py`, `consultation/pipeline.py` |
| 현재 Neon corpus 존재량 | `미확인` | 외부 DB 조회 금지. 저장소의 과거 benchmark artifact는 존재 |

`/api/rag/search` Router docstring은 아직 hashing 임베딩이라고 설명하지만 실제 Backend 기본값은 `remote_dual`이다. 문서 주석이 코드보다 오래됐다.

## 10. Embedding / Vector DB 구조

### 10.1 모델과 검색 설정

| 항목 | 실제 코드 기준 |
|---|---|
| Provider | 원격 HTTP 2개 (`remote_dual`) |
| 모델 ID | `jina-v4`, `medical-bgem3` 기본값 |
| 차원 | 둘 다 1024 강제 |
| normalize | Backend가 응답 vector의 L2 norm을 계산해 다시 정규화 |
| batch | 기본 32, 최대 64 |
| 요청 유형 | 문서 `passage`, 질문 `query` |
| DB metric | pgvector cosine distance |
| 후보 수 | `max(top_k×4, EMBEDDING_SEARCH_CANDIDATES=20)` |
| 최종 Top-K | 상담 기본 5 |
| 결합 | RRF, 기본 상수 60 |

### 10.2 관계

```text
admin_documents 1
  └─ N document_chunks 1
       └─ N chunk_embeddings
             ├─ provider_name = jina-v4
             └─ provider_name = medical-bgem3
```

`document_chunks.embedding VECTOR(1024)`는 기존 단일 embedding 컬럼으로 보이며 현재 Repository 검색·저장은 정규화된 `chunk_embeddings` 테이블을 사용한다.

### 10.3 중요한 스키마 불일치

- 최신 Alembic `a1f3c9d2e8b4`는 `chunk_embeddings.embedding`을 `VECTOR(1024)`로 변경한다.
- `DocumentChunkRepository.EMBEDDING_COLUMN_WIDTH`도 1024다.
- 그러나 `backend/app/models/generated.py`의 `ChunkEmbeddings.embedding`은 여전히 `VECTOR(2048)`다.

DB가 최신 migration 상태라면 ORM 타입과 실제 컬럼 타입이 다르다. 실제 insert/search 동작에 미치는 영향은 DB 연결 테스트 없이 단정할 수 없지만, autogenerate·binding·운영 정합성 위험이 높은 상태다.

## 11. Database 구조

### 11.1 세션과 스키마

- `core/database.py`: 전역 SQLAlchemy engine, `pool_pre_ping=True`, 요청별 `SessionLocal`.
- `core/config.py`: `postgresql://`를 `postgresql+psycopg://`로 변환한다.
- 기본 관리 스키마는 `app_db,vector_db`다.

### 11.2 코드 기준 ERD

```text
app_db.users
  ├─< app_db.conversations
  │    └─< app_db.messages
  │          └─< app_db.message_attachments
  ├─< app_db.consultation_logs
  └─< vector_db.admin_documents (uploaded_by nullable)
          └─< vector_db.document_chunks
                  └─< vector_db.chunk_embeddings

app_db.email_verifications  (email 문자열 기준, users FK 없음)
app_db.guest_ip_throttle    (IP별 독립 rate-limit row)

consultation_logs → users, conversations, messages FK
```

Admin OCR 저장은 `uploaded_by`를 설정하지 않는다. 현재 다수 저장 endpoint에 현재 관리자 주입 자체가 없으므로 누가 등록한 문서인지 추적되지 않는다.

### 11.3 Migration 주의사항

최초 migration `5d7e62474617_create_tables.py`의 `upgrade()`는 `pass`다. 뒤 migration들은 이미 존재하는 `users`와 vector schema/table을 전제로 `ALTER` 또는 추가 table 생성을 한다. 따라서 빈 PostgreSQL에서 `alembic upgrade head`만으로 전체 초기 스키마를 만들 수 없는 것으로 판단된다. README의 신규 환경 안내와 충돌한다.

## 13. Prompt 구조

의료 상담 Prompt의 단일 중심은 `ai/consultation/prompts/system_prompt.md`다.

```text
System Prompt
+ 참고용 진료과 정보
+ [참고 의료 정보] 최대 5개
+ [사용자 질문]
→ ProviderGenerateRequest(max_output_tokens=512)
→ LLM
→ response_validator
```

Prompt는 확정 진단·처방 용량 금지, 응급 대응, RAG 인젝션 무시, 질문 언어 유지, 정보 부족 시 확인 질문, Markdown 금지를 명시한다. 별도의 Prompt version 상수나 버전 파일명은 없다. Admin LLM 탭은 이 의료 상담 Prompt를 쓰지 않고 사용자가 입력한 raw prompt를 원격 모델에 직접 보낸다.

## 15. Admin 구조

### 15.1 OCR/RAG 등록 탭

- 복수 파일 또는 URL 입력
- chunk size와 overlap 비율 설정
- 20MB 이하 비동기 OCR Job, 20MB 초과 R2 multipart/streaming
- 진행률 polling, 추출 text·chunk·confidence·검토 필요 상태 표시
- 사용자의 명시적 저장 버튼 후 이중 embedding 및 Neon 저장
- `미구현`: 엔진 수동 선택

### 15.2 LLM 탭

- `GET /admin/llm/models`로 5개 모델과 원격 availability 조회
- 개별 실행은 `POST /admin/llm/run`
- 전체 비교는 Frontend가 실행 가능한 각 모델의 단일 실행 API를 `Promise.allSettled`로 병렬 호출
- 응답 시간, input/output/total token, provider/model, finish reason, Mock 여부 표시
- 브라우저 `AbortController` 취소는 결과 반영만 중단하며 Backend/원격 추론 취소를 보장하지 않음
- 첨부파일은 최대 5개 이름만 `documentNames`로 전송하고 실제 파일 내용은 전송하지 않음
- `/admin/llm/compare`와 `/llm/compare`는 현재 Admin UI에서 호출하지 않는 중복 공개 계약

현재 Registry는 `remote-http`만 사용하므로 정상 응답의 `isMock`은 false다. Mock Provider 파일과 UI 표시는 회귀 테스트/호환용으로 남아 있다.

### 15.3 평가 탭

- 정답 데이터 파싱(JSON/JSONL/CSV/TXT/직접 입력)
- 붙여 넣은 모델 답변에 exact match, token F1, 문자 유사도 계산
- retrieval 평가 endpoint 존재
- 그러나 Admin retrieval 평가 Service는 Provider를 전달하지 않아 `HashingEmbeddingProvider` 기본값을 사용한다. 현재 실제 서비스의 Jina+BGE+RRF 품질을 측정하지 않는다.
- 별도 `scripts/run_retrieval_benchmark.py` 결과 파일에는 420개 질문 기준 Jina/BGE/RRF 결과가 있지만 UI endpoint와 다른 경로다.

## 16. Docker / 배포 구조

### 16.1 로컬 실행

```text
run.bat
├─ backend/.venv Python 3.12 검사
├─ uvicorn app.main:app --reload      → localhost:8000
└─ npm run dev                        → localhost:5173
```

DB·R2·LLM·Embedding은 로컬 컨테이너가 아니라 외부 서비스다. `stop.bat`은 개발 포트와 Ollama 프로세스를 종료한다.

### 16.2 Docker

- `backend/dockerfile` 하나만 존재한다.

- Frontend Dockerfile과 docker-compose가 없다.
- DB, R2, LLM, 임베딩 서버 컨테이너 정의가 없다.

따라서 Docker만으로 전체 서비스를 한 번에 올릴 수 없다. Backend 단일 이미지와 외부 의존성을 연결하는 구조다.

### 16.3 배포

```text
Backend source
→ cloudbuild.yaml
→ Docker build/push
→ Artifact Registry
→ Cloud Run `the-gpt-dev` (asia-northeast3)

Frontend source
→ Vite dist
→ wrangler.jsonc assets
→ Cloudflare Workers static SPA

Browser/API proxy 및 OAuth root callbacks
→ 코드 주석상 Cloudflare Worker
→ 실제 Worker proxy source/config는 저장소에서 미확인
```

GitHub Actions나 branch→배포 workflow는 저장소에서 확인되지 않았다. Cloud Build trigger가 GitHub branch와 연결됐는지는 외부 설정이라 미확인이다.

배포상 핵심 공백은 다음과 같다.

- `cloudbuild.yaml`은 env/Secret 주입, migration 실행, `--no-cpu-throttling`, instance 수 제한을 선언하지 않는다.
- Frontend build 시 `VITE_API_URL`이 없으면 배포 bundle도 `http://localhost:8000/api`를 사용한다. 현재 로컬 `.env`에는 이 변수가 없다. 외부 Cloudflare build variable 설정은 미확인이다.
- Cloudflare Worker가 API proxy를 한다는 주석은 있으나 저장소에는 proxy 구현이 없다.
- 원격 embedding `/v1/embeddings` 서버 구현은 저장소에 없다.

## 19. 중복 구현 분석

### 19.1 OCR

핵심 코어는 통합됐다. `hybrid_ocr`는 별도 구현이 아니라 re-export다. Web과 대용량 streaming은 입력 특성이 달라 독립 Adapter가 합리적이다.

### 19.2 LLM

```text
현재 서비스 경로
└─ llm_runtime ModelRegistry → RemoteHttpLlmProvider

실험/호환 경로
├─ ai.llm.registry legacy model IDs
├─ MedGemma/Qwen/Llama local providers + engine
├─ OllamaProvider
└─ MockLlmProvider
```

두 Registry가 서로 다른 ID와 설명을 관리해 모델 추가 시 drift 가능성이 있다. 실제 Web 기준 단일 진실 공급원은 `backend/app/services/llm_runtime.py`다.

### 19.3 API

- LLM 비교가 `/api/llm/compare`와 `/api/admin/llm/compare` 두 계약으로 존재한다.
- 현재 Admin UI는 둘 다 쓰지 않고 `/api/admin/llm/run`을 모델별로 호출한다.
- `/api/admin/ocr/analyze` 동기 응답 경로와 `/api/admin/ocr/jobs` 비동기 경로가 함께 있으나 UI는 Job 경로만 쓴다.
- `profileImageApi.ts`만 공통 `apiClient`를 우회한다.

### 19.4 DB/Embedding

legacy `document_chunks.embedding`과 provider별 `chunk_embeddings.embedding`이 공존한다. 현재 실제 경로는 후자다. ORM/마이그레이션 차원 불일치까지 있어 정리 우선순위가 높다.

```text
→ 진료과 분류 + Jina/BGE 이중 Vector 검색
→ RRF Top-5 의료 context
→ 안전 Prompt + 원격 파인튜닝 LLM
→ 응답 후처리와 상담 로그
→ React 채팅 UI
```

### 25.2 강조할 기술적 포인트

- PDF의 native/scanned/hybrid 페이지를 구분하고 Office·구조화 text·ZIP·웹 URL까지 하나의 OCR 코어로 처리한다.
- 서로 특성이 다른 Jina와 Medical BGE 검색 순위를 RRF로 결합하고, 출처 신뢰도와 진료과를 soft boost로 반영한다.
- 모델과 Provider를 분리한 Registry로 메인 상담과 Admin 비교가 동일한 5개 원격 모델을 공유한다.
- 응급 키워드 사전 차단, Prompt 안전 규칙, 출력 validator의 다중 안전 경계를 둔다.
- 대용량 파일은 Browser→R2 multipart 후 streaming 처리해 Cloud Run 본문 크기 제한을 피한다.

발표에서는 “완성된 의료 진단 시스템”이 아니라 “의료 상담 보조·검색 시스템”으로 표현해야 한다. 채팅 첨부 본문 미연결, 임상 검증 미확인, 운영 Job 안정성 문제도 한계로 명확히 공개하는 것이 정확하다.

## 26. 핵심 질문 15개 답변

1. **핵심 Backend 진입점은?** `backend/app/main.py`의 `app = create_app()`.
2. **의료 상담은 어디서 시작되는가?** `POST /api/conversations/{conversation_id}/messages`; 별도 consultation Router는 비어 있다.
3. **LLM은 어디서 호출되는가?** `MessageService` → `ai.consultation.consult()` → `llm_application.run()` → `RemoteHttpLlmProvider` → Vast.ai `/v1/generate`.
4. **RAG는 실제 서비스에 연결됐는가?** 코드상 연결됨. live Neon 데이터량과 원격 embedding 상태는 미확인이다.
5. **OCR 구현은 몇 개인가?** 공통 OCR 코어 1개와 입력별 Adapter(일반 파일, Web, 대용량 streaming) 3경로다.
6. **Embedding 모델은?** 기본 `jina-v4`와 `medical-bgem3`, 각각 1024차원, 정규화됨.
7. **Vector DB는 어디인가?** Neon PostgreSQL `vector_db.document_chunks`와 `vector_db.chunk_embeddings`의 pgvector.
8. **Admin OCR과 사용자 OCR은 같은 Pipeline인가?** 일반 파일은 같은 `ai.ocr.analyze_document()`를 쓴다. Admin은 Chunk/Job/저장을 추가한다. Web/대용량은 별도 Adapter다.
9. **Admin LLM 비교는 실제 호출인가 Mock인가?** 실제 원격 호출이다. Mock Provider는 현재 Registry에 없다.
10. **Docker 실행 시 무엇이 올라오는가?** Dockerfile 기준 Backend 하나만 올라온다. 로컬 `run.bat`은 Backend와 Vite Frontend를 올린다.
11. **Cloudflare 배포 구조는?** Frontend 정적 Worker assets와 R2 사용이 확인된다. API proxy Worker 구현은 저장소에 없다. Backend는 Cloud Run이다.
12. **가장 큰 기술적 위험은?** Admin Backend 인가 누락. 그다음은 메모리 OCR Job 운영 안정성, DB vector schema drift다.
13. **제거 가능한 Mock/임시는?** 사용처 없는 OCR Mock, AppLayout, 일부 legacy API/Registry와 dead dependency가 후보지만 외부 사용 확인 후 제거해야 한다.
14. **인수인계 시 가장 먼저 볼 파일은?** `backend/app/services/message.py`; 전체 상담 가치 흐름이 가장 많이 모인다. 그 전에 `main.py`/`api/router.py`로 진입점을 확인한다.
15. **가장 단순한 아키텍처 표현은?** `React → FastAPI → (Neon + OCR + Jina/BGE RAG + Vast.ai LLM) → 상담 응답`.

## 27. 최종 결론

프로젝트는 핵심 데모 흐름이 단순 Mock 단계를 넘어 실제 OCR·RAG·원격 LLM까지 연결된 상태다. 특히 AI 코어 분리, OCR 통합, 이중 embedding과 RRF, 공통 LLM Registry, 응급/fallback 경계는 인수인계 가능한 수준으로 구조화돼 있다.

다만 “운영 가능한 1차 완성”으로 보기 전에 세 가지를 먼저 해결해야 한다. 첫째, 모든 Admin API의 서버 측 관리자 인가를 일관되게 적용해야 한다. 둘째, 메모리 OCR Job을 durable queue/store로 옮기거나 최소한 Cloud Run 단일 instance·instance-based CPU 조건을 명시해야 한다. 셋째, ORM·migration·실제 Neon의 vector 차원을 1024로 일치시키고 빈 DB bootstrap migration을 완성해야 한다.

그 다음 우선순위는 Frontend production API URL/proxy 확정, 실제 Jina+BGE+RRF 평가의 Admin 연결, 채팅 첨부 본문과 상담 연결, Frontend 자동 테스트 도입이다. 이 순서로 정리하면 데모 완성도를 유지하면서 보안·재현성·운영 안정성을 크게 높일 수 있다.
