# RAG 프롬프트 평가 스크립트 구현 보고

- 작업일: 2026-09-04
- 작업 영역: Python CLI / RAG Evaluation
- 대상 기능: 기존 Neon RAG와 Remote MedGemma를 이용한 프롬프트 평가
- 주요 기술: Python, SQLAlchemy, pgvector, JSON/JSONL, 기존 AI Core
- 작업 범위: 단일 평가 스크립트, Live/Snapshot 모드, 로컬 결과 기록, 정적 안전 점검
- 제외 범위: 실제 Neon/Embedding/LLM 호출, V4.2 작성, 기존 서비스/API/DB Schema 수정, Frontend 수정

## 1. 작업 목적

기존 프로젝트에는 질문 Embedding, Neon Vector 검색, RRF 결합, RAG Context 생성,
Remote MedGemma 호출 경로가 이미 있다. 이번 작업은 이 기능을 다시 구현하지 않고
고정 질문 5개와 외부 Prompt JSON을 조합해 결과를 비교할 수 있는 읽기 전용 평가
진입점을 추가하는 것이 목적이다.

첫 Live 실행에서 Retrieval 결과를 로컬 Snapshot으로 남기고, 다음 Prompt 버전은 같은
Snapshot을 사용한다. 이 방식으로 V3.8과 V4.1의 비교에서 검색 결과가 바뀌는 변수를
제거할 수 있다.

## 2. 작업 전·후 상태

작업 전:

```text
메인 채팅 API
→ MessageService
→ 사용자/답변/상담 로그 DB 저장
→ 기존 RAG 검색
→ 기존 상담 Prompt
→ Remote MedGemma
```

메인 채팅 경로는 DB Write가 포함되고 다른 Prompt JSON을 직접 주입할 수 없었다.

작업 후:

```text
rag_prompt_eval.py
→ 기존 RAG 검색(Neon READ)
→ Retrieval Snapshot 로컬 기록
→ 기존 Context Builder
→ 지정 Prompt JSON
→ 기존 Remote LLM Application
→ TXT/JSONL 로컬 기록
```

`MessageService`와 메시지·상담 로그 Repository를 거치지 않는다.

## 3. 생성 파일

| 파일 | 역할 |
| --- | --- |
| `scripts/rag_prompt_eval.py` | Live/Snapshot 평가 전체 순서를 관리하는 단일 CLI |
| `docs/2_reports/22_RPT_RAG_프롬프트평가스크립트_구현보고_20260904.md` | 구현 구조, 안전 경계, 실행·검증 방법 기록 |

기존 Backend, AI Core, Frontend 파일은 수정하지 않았다.

## 4. 중심 함수와 전체 실행 흐름

중심 함수는 다음과 같다.

```text
run_evaluation()
```

이 함수가 Prompt 검증, 질문 선택, 모드별 Retrieval, LLM 호출, 결과 기록 순서를
끝까지 관리한다.

```text
run_evaluation()
→ load_prompt_config()
← version/system_prompt/rag_context_template
→ Live 고정 질문 또는 Snapshot 질문 로드
← 선택된 질문 목록
→ retrieve_live() 또는 load_snapshot()
← RetrievedChunk 호환 목록
→ compose_user_prompt()
   → build_reference_info_block()
← system/user message 입력
→ generate_answer()
   → llm_application.run("medgemma", request)
← LlmExecutionResult
→ TXT/JSONL/Snapshot/run_info 로컬 기록
```

한 문항의 Retrieval 또는 LLM 호출이 실패하면 오류 단계와 예외 타입만 기록하고 다음
문항으로 이동한다. 일부 실패가 있으면 프로세스 종료 코드는 `1`, 입력 준비 오류는 `2`,
전 문항 성공은 `0`이다.

## 5. 재사용한 기존 모듈

| 순서 | 기존 파일 | 함수/객체 | 역할 |
| ---: | --- | --- | --- |
| 1 | `backend/app/core/rag_embedding.py` | `get_default_rag_embedding_providers()` | 기존 검색용 Embedding Provider 준비 |
| 2 | `backend/app/services/rag_search_service.py` | `search()` | 질문 Embedding, provider별 Vector 검색, RRF/soft boost, Top-K 반환 |
| 3 | `backend/app/repositories/document_chunk.py` | `search_by_provider()` | 기존 Neon pgvector SELECT 수행 |
| 4 | `ai/consultation/context.py` | `build_reference_info_block()` | 검색 청크를 기존 `[참고 의료 정보]` 형식으로 변환 |
| 5 | `ai/llm/contracts.py` | `LlmMessage`, `ProviderGenerateRequest` | System/User 메시지와 생성 요청 구성 |
| 6 | `backend/app/services/llm_runtime.py` | `llm_application` | `medgemma`를 기존 Remote HTTP Provider에 연결 |
| 7 | `ai/llm/application.py` | `run()` | 모델 Registry와 Provider 실행 조율 |

Repository Query, Embedding HTTP Client, RRF, LLM HTTP Client를 평가 스크립트에
복사하지 않았다.

## 6. DB Read / Write 여부

### Live 모드

허용되는 흐름만 사용한다.

```text
질문 Embedding 생성(메모리)
→ 기존 chunk_embeddings Vector SELECT
→ RRF/soft boost(메모리)
→ Top-5 반환
```

- DB Session에서 `commit()`을 호출하지 않는다.
- 질문 Vector, 질문, 답변, 로그를 Neon에 저장하지 않는다.
- `MessageService` 및 저장 Service/Repository를 import하지 않는다.
- 질문마다 독립 Session을 만들고 마지막에 `rollback()`과 `close()`를 수행한다.
- PostgreSQL/Neon에서는 검색 전에 `SET TRANSACTION READ ONLY`를 적용한다. 실수로
  쓰기 Query가 추가되더라도 DB가 해당 트랜잭션을 거부하는 2차 안전장치다.
- PostgreSQL 이외 dialect에서는 위 SQL 안전장치를 적용하지 않지만, 호출 경로는
  동일하게 기존 `rag_search_service.search()`로 제한된다.

### Snapshot 모드

`SessionLocal`, RAG 검색 Service, Embedding Provider를 준비하지 않는다. 입력 JSON의
청크를 `SnapshotChunk`로 복원한 뒤 Context Builder와 Remote LLM만 사용한다.
따라서 Neon Query와 질문 Embedding 호출이 모두 없다.

## 7. Prompt 로딩 방식

스크립트 최상단에 V3.8과 V4.1 파일을 각각 지정한다. 기본 선택 버전도 같은 영역에서
한 줄로 바꿀 수 있다.

```python
PROMPT_V3_8_FILE = Path("...")
PROMPT_V4_1_FILE = Path("...")
DEFAULT_PROMPT_VERSION = "v4.1"
PROMPT_PRESETS = {
    "v3.8": {...},
    "v4.1": {...},
}
```

CLI에서는 `--prompt-version v3.8` 또는 `--prompt-version v4.1`로 preset을 선택한다.
옵션을 생략하면 `DEFAULT_PROMPT_VERSION`을 사용한다. 기존처럼 임의의 JSON을 시험할
수 있도록 `--prompt-file`도 선택적 override로 유지했으며, 두 옵션은 동시에 사용할 수
없다.

실제 파일 구조를 확인한 결과 V4.1에는 다음 세 값이 JSON 최상위에 있다.

```json
{
  "version": "v4.1",
  "system_prompt": "...",
  "rag_context_template": "...{rag_context}...{question}..."
}
```

반면 V3.8에는 `version`과 `system_prompt`만 있고 `rag_context_template`은 없다. 같은
RAG 입력 조건으로 비교하기 위해 V3.8 preset은 V3.8의 System Prompt와 V4.1 JSON의
RAG Context Template 파일을 별도로 지정한다. V4.1 preset은 두 값을 모두 V4.1 JSON에서
읽는다. 프롬프트 문자열을 Python 코드에 복사하지 않는다.

로더는 다음을 검증한다.

- JSON 최상위가 객체인지
- `version`, `system_prompt`가 비어 있지 않은 문자열인지
- 현재 JSON 또는 별도 Template JSON에 `rag_context_template`이 있는지
- 템플릿에 `{rag_context}`와 `{question}`이 모두 있는지
- preset 선택 버전과 실제 JSON `version`이 일치하는지

`system_prompt`는 `system` 역할 메시지로 전달한다. 기존
`build_reference_info_block()`의 결과와 사용자 질문은 V4.1
`rag_context_template`에 각각 치환해 `user` 역할 메시지로 전달한다. 검색 결과가 없으면
가상 근거를 만들지 않고 `(검색된 참고 문서 없음)` 상태만 명시한다.

확인한 원본 경로는 다음과 같다.

```text
G:\내 드라이브\02_프로젝트\3_메인프로젝트\06_FineTuning\00_common\prompts\medical_prompt_v3.8.json
G:\내 드라이브\02_프로젝트\3_메인프로젝트\06_FineTuning\00_common\prompts\medical_prompt_v4.1_rag_prototype.json
```

프롬프트 원문은 이번 작업에서 저장소로 복사하지 않았다.

## 8. Live 모드

Live 모드는 다음 순서로 실행된다.

```text
고정 질문
→ 기존 Jina/BGE Provider의 embed_query()
→ Neon provider별 Vector SELECT
→ 기존 RRF/soft boost
→ Top-5 RetrievedChunk
→ Snapshot 즉시 기록
→ Context/Prompt 구성
→ Remote MedGemma
→ TXT/JSONL 기록
```

Embedding Provider 인스턴스는 실행 시작 시 한 번 준비해 모든 질문에서 재사용하고,
DB Session은 문항 실패를 서로 격리하기 위해 질문마다 새로 연다. Snapshot은 LLM 호출보다
먼저 기록하므로 LLM 실패가 발생해도 성공한 Retrieval 결과가 남는다.

Snapshot의 `retrieval_config`에는 실행 시 확인한 다음 값을 기록한다.

```text
top_k
use_reranker
providers
embedding_dimension
candidate_min
rrf_k
```

## 9. Snapshot 모드

Snapshot 모드는 `--snapshot`으로 받은 JSON에서 질문과 청크 순서를 복원한다.

```text
retrieval_snapshot.json
→ Snapshot 유효성 검사
→ SnapshotChunk 복원
→ 기존 Context Builder
→ 새 Prompt JSON
→ Remote MedGemma
```

각 청크의 `content`, `source`, `metadata`, ID, score와 제공된 선택 필드를 보존한다.
새 실행의 결과 폴더에도 입력 Snapshot 전체를 복사한다. `--limit` 또는
`--question-id`를 사용하면 LLM 평가 문항만 제한되고 복사된 Snapshot 원본 내용은
축소하지 않는다.

## 10. Retrieval 및 출력 데이터

현재 `RetrievedChunk`에 실제 존재하는 값을 우선 저장한다.

```text
rank
content
score
chunk_id
document_id
source
metadata
```

`title`, `url`, `distance`는 객체 또는 실제 metadata에 값이 있을 때만 추가한다. 현재
기본 검색 Service는 raw cosine distance를 최종 `RetrievedChunk`로 전달하지 않으므로
가상의 distance를 생성하지 않는다. `score`는 기본 경로에서 cosine similarity가 아니라
RRF와 soft boost가 반영된 최종 점수다.

기존 Context Builder 정책에 따라 LLM Context는 최대 5개, 청크당 기본 800자로 제한된다.
Snapshot에는 축약 전 `RetrievedChunk.text`를 기록하므로 이후에도 같은 Builder 정책으로
Context를 재생할 수 있다.

## 11. 출력 파일 구조

매 실행마다 초 단위 timestamp 폴더를 만든다. 같은 초에 폴더가 이미 있으면 `_01`,
`_02` 순번을 붙여 기존 결과를 덮어쓰지 않는다.

```text
outputs/rag_eval/YYYYMMDD_HHMMSS/
├─ rag_v4.1_result.txt
├─ rag_v4.1_debug.jsonl
├─ retrieval_snapshot.json
└─ run_info.txt
```

### 결과 TXT

문항별 질문, category, Retrieval 전체, 최종 답변, Prompt 버전, Retrieval/LLM/전체
소요 시간을 기록한다.

### Debug JSONL

문항별 한 줄 JSON으로 다음 값을 기록한다.

```text
question_id, category, prompt_version, mode
retrieval_count, retrieval_elapsed_seconds
llm_elapsed_seconds, total_elapsed_seconds
max_output_tokens
input_tokens, output_tokens, total_tokens, finish_reason
success, error.stage, error.type
```

예외 메시지는 연결 문자열이나 Secret이 섞일 가능성을 피하기 위해 기록하지 않고 예외
타입만 기록한다.

### run_info.txt

시작/완료 시각, 상태, Prompt 버전/경로, RAG Template 경로, 문항 성공·실패 수, 모드,
Embedding 모델, Top-K, reranker 사용 여부, Remote 모델, 서버 routing key,
`max_output_tokens`, Snapshot 경로, 전체 시간을 기록한다. API Key, DB 비밀번호,
환경변수 실제 값은 기록하지 않는다.

## 12. Remote LLM 호출과 Generation 설정

평가 스크립트는 로컬 Hugging Face 모델을 로드하지 않는다.

```text
ProviderGenerateRequest
→ llm_application.run("medgemma", request)
→ RemoteHttpLlmProvider
→ POST /v1/generate
```

`medgemma` 공개 모델 ID는 현재 Registry에서 Remote server routing key인
`LLM_REMOTE_MEDGEMMA_FINAL_MODEL`에 연결된다. `run_info.txt`의 `Adapter` 값은 실제 GPU
메모리 상태를 검사한 결과가 아니라 이 확인 가능한 routing key임을 함께 표시한다.

현재 Backend 계약에서 지원하는 `max_output_tokens`만 `256`으로 명시한다. 다음 값은
평가 스크립트에서 새로 구현하거나 요청에 추가하지 않으며 Remote LLM Server 설정을
그대로 사용한다.

```text
do_sample
temperature
top_p
repetition_penalty
no_repeat_ngram_size
EOS / EOT
```

## 13. 실행 방법

프로젝트 루트에서 실행한다. 설정은 프로젝트 루트 `.env`, 없으면 `backend/.env`에서
기존 Backend 설정 로더가 읽는다.

### 첫 1문항 Live 테스트

지시문에 따라 실제 첫 실행은 아래 둘 중 하나를 사용한다.

```powershell
python scripts/rag_prompt_eval.py `
  --prompt-version v4.1 `
  --mode live `
  --limit 1
```

또는 질문 ID를 고정한다.

```powershell
python scripts/rag_prompt_eval.py `
  --prompt-version v4.1 `
  --mode live `
  --question-id rag_01
```

### 전체 5문항 Live 테스트

한 문항의 Retrieval, Remote LLM 전달, 출력 파일과 DB 무변경을 확인한 뒤 실행한다.

```powershell
python scripts/rag_prompt_eval.py `
  --prompt-version v4.1 `
  --mode live
```

### V3.8 Snapshot 비교 테스트

V4.1 Live 실행에서 생성된 실제 timestamp를 아래 변수에 넣는다. V3.8은 Neon을 다시
검색하지 않고 동일 Retrieval을 사용한다.

```powershell
$RAG_SNAPSHOT_PATH = "outputs\rag_eval\YYYYMMDD_HHMMSS\retrieval_snapshot.json"
python scripts/rag_prompt_eval.py `
  --prompt-version v3.8 `
  --mode snapshot `
  --snapshot $RAG_SNAPSHOT_PATH
```

상단 preset에 없는 임의 Prompt JSON은 `--prompt-file`로 지정할 수 있다. 이 파일은
자체 `rag_context_template`을 포함해야 한다.

## 14. 실제 실행 전 확인 항목

- `DATABASE_URL`이 대상 Neon DB를 가리키는지 확인한다.
- `EMBEDDING_REMOTE_BASE_URL`, `EMBEDDING_API_KEY`가 설정되어 있는지 확인한다.
- `LLM_REMOTE_ENABLED=true`, `LLM_REMOTE_BASE_URL`, `LLM_REMOTE_API_KEY`를 확인한다.
- 현재 Embedding Provider 이름과 DB의 `chunk_embeddings.provider_name`이 일치하는지
  READ-only Query로 확인한다.
- Live DB가 최신 마이그레이션 상태인지 확인한다.
- V3.8/V4.1 상단 경로가 현재 환경에서 접근 가능한지 확인한다.
- V4.1 JSON이 UTF-8이고 `rag_context_template`과 두 자리표시자를 포함하는지 확인한다.
- `outputs/rag_eval/`을 버전 관리하거나 외부 공유할지 별도 정책을 확인한다. Retrieval
  문서나 평가 질문에 민감정보가 들어가는 경우 출력 파일 취급에 주의한다.
- 최초에는 반드시 `--limit 1` 또는 `--question-id rag_01`을 사용한다.

## 15. 정적 테스트 및 검증 결과

요구사항에 따라 실제 스크립트 실행, Neon 연결, 원격 Embedding, Remote LLM 호출은 하지
않았다. `outputs/rag_eval` 폴더도 생성되지 않은 것을 확인했다.

| 점검 | 결과 |
| --- | --- |
| Python AST 구문 분석 | 통과 |
| Ruff 정적 검사 | 통과 |
| Ruff format 검사 | 통과 |
| DB 쓰기 SQL 키워드 검사 | 없음 |
| 저장/메시지 전송 계열 함수 호출 AST 검사 | 없음 |
| `MessageService` import 검사 | 없음 |
| 기존 `rag_search_service.search()` 호출 | 확인 |
| 기존 `build_reference_info_block()` 호출 | 확인 |
| 기존 `llm_application.run()` 호출 | 확인 |
| 로컬 Hugging Face 모델 로드 호출 검사 | 없음 |

이 결과는 코드의 정적 구조가 요구사항을 만족한다는 뜻이다. 실제 Neon 데이터,
Embedding 서버, LLM 서버, 모델 응답과 생성된 네 출력 파일은 아직 검증하지 않았다.

## 17. 확인된 제한 사항과 후속 확인

- Prompt 효과만 비교하기 위해 `consult()`의 응급 하드 필터와 응답 validator를 거치지
  않는다. 응급 문항은 선택한 V3.8 또는 V4.1 System Prompt 자체의 안전 동작을 평가한다.
- 운영 채팅의 진료과 classifier를 호출하지 않으므로 source tier boost는 적용되지만
  department soft boost는 적용되지 않는다. 동일 Snapshot 기반 Prompt 비교에는 영향이
  없지만 운영 전체 파이프라인 재현 평가와는 구분해야 한다.
- 검색 Service가 raw cosine distance, DB 문서 URL, DB `chunk_index`를 최종 결과로
  전달하지 않으므로 이번 파일은 해당 값을 새로 만들지 않는다.
- `ChunkEmbeddings` ORM의 Vector 폭 선언과 최신 마이그레이션/Repository 상수가
  일치하는지는 실제 DB 연결 전에 별도로 확인해야 한다.
- Snapshot은 Context 입력을 고정하지만 Remote server의 sampling/seed를 제어하지 않는다.
  현재 Backend 계약에 없는 Generation parameter는 이번 작업에서 확장하지 않았다.
- `Adapter` 기록은 Backend Registry의 요청 routing key다. 서버가 실제로 어떤 Adapter를
  메모리에 적용했는지는 Remote server log 또는 debug 정보로 별도 확인해야 한다.
- 실제 실행 후에는 `finish_reason`, token 수, Retrieval 0건, 동일 문서 편중, 응급 답변
  형식, Context/질문 경계를 우선 확인해야 한다.

## 18. 추천 코드 읽기 순서

```text
1. scripts/rag_prompt_eval.py의 QUESTIONS/상수와 parse_args()
2. run_evaluation() 중심 흐름
3. retrieve_live()의 읽기 전용 검색 경계
4. backend/app/services/rag_search_service.py의 search()
5. ai/consultation/context.py의 build_reference_info_block()
6. generate_answer()의 Message/Request 구성
7. backend/app/services/llm_runtime.py의 모델 Registry
8. ai/llm/providers/remote_http.py의 /v1/generate 요청
9. append_result_text()/append_jsonl()/build_run_info() 출력 구조
```

`run_evaluation()`로 다시 돌아오면 각 하위 함수의 결과가 다음 단계로 어떻게 전달되는지
전체 흐름을 확인할 수 있다.
