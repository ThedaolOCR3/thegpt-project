## 2. 결론 요약

### 2.1 최종 판단

현재 프로젝트는 추출, 최소 공백 정리, 문자 Chunk, Jina/BGE 이중 Embedding, 세 테이블 저장, provider별 pgvector 검색, RRF, 상담 LLM Context 연결까지 이미 동작 경로가 있다.

추가해야 할 핵심은 다음 네 가지다.

1. 추출 결과와 Chunk 사이의 **공통 RAG Cleaning 단계**
2. `raw_text`와 `cleaned_text`의 **Job·저장 계약 분리**
3. 문서 단위 **최소 Metadata 저장 컬럼**
4. 정제 결과와 Metadata를 확인하는 **Admin Preview/Input UI**

따라서 전체 RAG 구조를 다시 만들 필요는 없다. 다만 현재 Schema에는 문서 제목·출처 유형·Metadata·정제본을 보존할 공간이 없으므로, Metadata를 문자열 본문에 억지로 삽입하지 않는 한 DB Migration은 필요하다.

### 2.2 유지할 구조

```text
유지
├─ Admin RAG 탭과 Job 방식
├─ ai/ocr 추출기
├─ 웹 본문 DOM 추출과 내부 이미지 OCR
├─ backend 문자 Chunker(최소 구현 기준)
├─ Jina/BGE 원격 Provider
├─ chunk_embeddings provider 행 구조
├─ inline 문서의 단일 Transaction 저장
├─ provider별 pgvector 검색
├─ UUID 기반 RRF
└─ 메인 채팅의 RAG Context 연결
```

### 2.3 새로 추가할 최소 범위

```text
추출 결과(raw)
→ 공통 RAG Cleaning Service
→ cleaned_text + cleaning 결과/경고
→ 문서 Metadata 결합
→ 현재 문자 Chunker
→ 현재 Jina/BGE
→ 현재 3단 테이블 저장
```

DB 최소안은 `vector_db.admin_documents`에 다음을 추가하는 것이다.

| 컬럼 | 판단 | 목적 |
|---|---|---|
| `document_title` | 필요 | 파일명/HTML title을 DB에 영구 보존 |
| `source_type` | 필요 | URL, 일반 업로드, R2 업로드를 구분 |
| `cleaned_text` | 필요 | Embedding에 사용한 최종 정제본 보존 |
| `metadata JSONB` | 필요 | 출처기관·언어·라이선스·분류의 확장 가능한 저장 |
| `content_hash` | 권장 | 동일 정제 내용의 중복 등록 탐지 |

`metadata`는 SQLAlchemy Declarative의 `Base.metadata`와 이름 충돌을 피하기 위해 ORM 속성명을 `document_metadata` 등으로 매핑해야 한다.

### 2.4 중요한 예외

- **20MB 이하 inline 파일과 웹 URL**은 문서·Chunk·Embedding을 한 Transaction으로 저장한다.
- **20MB 초과 대용량 Text/ZIP 경로**는 문서 생성, Chunk 배치, 완료 표시를 여러 번 Commit하고 실패 시 부모 문서를 삭제하는 보상 처리 방식이다. 따라서 “모든 입력이 하나의 Transaction”이라는 기존 문서 설명은 대용량 경로에는 정확하지 않다.
- 대용량 경로의 `ocr_extracted_text`에는 전체 Text가 아니라 앞 100,000자 Preview만 저장된다.
- 로컬 `.html` 파일 업로드는 지원하지 않는다. HTML은 웹 URL 입력으로만 처리한다.

## 3. 목표 파이프라인

외부 팀 설계의 방향은 현재 코드와 대체로 일치한다.

```text
[Source]
File / URL
   ↓
[Extraction]
Document Text / HTML Main Text / Image OCR
   ↓
[Raw Document]
raw_text
   ↓
[Cleaning]
cleaned_text
   ↓
[Document Metadata]
title / source / license / language / category / topic
   ↓
[Chunking]
Chunk 0..N
   ↓
[Embedding]
jina-v4 passage + medical-bgem3 passage
   ↓
[Neon]
admin_documents → document_chunks → chunk_embeddings
   ↓
[Search]
Jina Top-N + BGE Top-N → RRF → Top-K
```

외부 설계와 현재 구현의 가장 큰 차이는 Chunk 기준이다.

| 항목 | 팀 설계 기준선 | 현재 Admin 실제값 | 공통 `ai/rag` 별도 구현 |
|---|---|---|---|
| 단위 | Token | 문자 | 근사 Token(`cl100k_base`) |
| 기본 크기 | 500~800 tokens | 512자 | 300 tokens |
| Overlap | 100 tokens | 10%, 기본 50자 | 60 tokens |
| 현재 Admin 저장 사용 | 목표 | 사용 중 | 미사용 |

외부 설계의 500~800 token은 확정 계약이 아니라 실험 기준선이다. 이번 최소 구현에서 Chunker까지 바꾸면 기존 Preview, 저장 Chunk 수, Embedding 비용, 검색 회귀 범위가 함께 커지므로 먼저 정제·Metadata를 붙이고 Chunk 전략은 평가 데이터로 별도 결정하는 편이 안전하다.

## 4. 현재 실제 파이프라인

### 4.1 20MB 이하 파일

```text
OcrPanel
→ useOcrTest.analyzeItem()
→ apiAdminAiService.createFileJob()
→ POST /api/admin/ocr/jobs
→ OcrJobManager.create_job()
→ OcrWorkflowService.process_document()
→ ai.ocr.analyze_document()
→ 형식별 Extractor
→ clean_document_text(extracted.text)
→ create_chunks(result.cleaned_text, 문자 수, 문자 overlap)
→ OcrDocumentResponse(extractedText=cleaned_text, chunks)
→ 메모리 OcrJob 완료
→ Frontend Polling 및 Text/Chunk Preview
→ POST /api/admin/ocr/vector-save {jobId}
→ save_ocr_result_with_embeddings()
→ RemoteDualEmbeddingService.embed_chunks(existing chunks)
→ DocumentRepository.save_with_chunks()
→ admin_documents + document_chunks + chunk_embeddings COMMIT
```

Frontend는 전체 Text나 Chunk를 저장 API로 다시 보내지 않고 `jobId`만 보낸다. 이 구조는 유지하는 것이 맞다.

### 4.2 웹 URL

```text
OcrPanel URL 입력
→ POST /api/admin/ocr/url-jobs
→ require_admin
→ OcrJobManager.create_url_job()
→ WebOcrWorkflowService.process_url()
→ WebDocumentFetcher.fetch_page()
→ parse_web_document()
→ 본문 후보 DOM 선택 + Block/Heading 추출 + 이미지 후보 수집
→ fetch_images()
→ build_web_ocr_result()
→ HTML 본문 뒤에 이미지 OCR Section append
→ create_chunks(result.cleaned_text)
→ Job/Preview
→ POST /api/admin/ocr/vector-save {jobId}
→ 기존 Jina/BGE 및 저장 경로 재사용
```

최종 Redirect URL은 `sourceUrl`로 Job에 남고 `admin_documents.original_file_url`에 저장된다.

### 4.3 20MB 초과 구조화 Text/ZIP

```text
Frontend R2 multipart upload
→ POST /api/admin/ocr/jobs/remote
→ LargeDocumentService
→ Text decode 또는 ZIP 내부 문서 순회
→ 고정 문자 Streaming Chunk
→ Chunk JSONL artifact를 R2에 저장
→ 앞 100,000자 / 앞 20 Chunk만 Preview
→ vector-save
→ admin_documents(processing) COMMIT
→ artifact Chunk를 Embedding batch 단위로 읽음
→ Chunk + Embedding batch별 COMMIT 반복
→ admin_documents(completed) COMMIT
→ Chunk artifact 삭제
```

대용량 경로는 다음 차이가 있다.

- 일반 `clean_document_text()`를 전체 원문에 적용하지 않는다.
- JSON/JSONL/CSV의 문법 검증을 inline 경로처럼 수행하지 않고 원문 Streaming한다.
- 자연 경계 탐색 없이 고정 문자 폭으로 분할한다.
- 저장되는 `ocr_extracted_text`는 전체 본문이 아니라 Preview다.
- R2 원본 Object 참조가 `original_file_url`에 남는다.

30개 내외 의료 문서가 대부분 20MB 이하라면 이번 최소 구현의 우선 범위는 inline 파일과 URL로 잡되, 대용량 경로의 의미 차이는 문서화하고 후속 호환 작업으로 남겨야 한다.

### 4.4 검색과 상담 연결

```text

→ MessageService._search_reference_chunks()
→ rag_search_service.search()
→ Jina query Embedding
→ provider_name='jina-v4' pgvector Top 20
→ Medical BGE query Embedding
```

## 5. 파일·URL·Text·OCR 처리 현황

| 입력 | 지원 | 실제 처리 | 구조 보존 | 이미지 OCR 결합 | 주의점 |
|---|---|---|---|---|---|
| PDF | 완료 | Digital/Scanned/Hybrid 분기 | `## 페이지 N`, Native Markdown 우선 | Hybrid는 이미지 Block 위치에 `[이미지 OCR]` 삽입 | 반복 Header/Footer 제거 없음 |
| PNG/JPG | 완료 | 전체 이미지를 PaddleOCR | OCR Line 순서 | 문서 전체가 OCR Text | Confidence 미달 Line은 Clean에서 제외, Raw에는 존재 |
| DOCX | 완료 | `python-docx` 직접 추출 | Heading, List, Markdown Table | 문서 Unit의 본문 뒤에 `### 이미지 OCR N` append | 이미지의 원래 문단 위치는 보존하지 않음 |
| PPTX | 완료 | 도형을 좌표순으로 직접 추출 | `## 슬라이드 N`, Table, 발표자 노트 | 슬라이드 Text 뒤에 이미지 OCR append | 복잡한 겹침·차트는 완전 재현 아님 |
| JSON | 완료 | inline은 파싱·들여쓰기, large는 원문 Streaming | JSON 구조 | 없음 | inline/large 의미 차이 |
| JSONL | 완료 | inline은 줄별 JSON 검증, large는 원문 Streaming | 줄 구조 | 없음 | inline/large 의미 차이 |
| CSV | 완료 | inline은 문법 검증 후 원문 유지, large는 원문 Streaming | 원문 | 없음 | 열 의미 Metadata 생성 없음 |
| TXT | 완료 | 디코딩 후 원문 | 줄 구조 | 없음 | 최소 공백 정리만 적용 |
| ZIP | 완료 | 지원 내부 문서 통합 | `## ZIP 내부 파일` | 내부 문서 처리에 따름 | large ZIP은 20MB 이하 binary member만 OCR |

| 로컬 HTML 파일 | 미구현 | 확장자 허용 목록에 없음 | 해당 없음 | 해당 없음 | URL 방식으로만 HTML 처리 |

## 6. 현재 Raw Text 구조

### 6.1 Job과 저장에 실제로 전달되는 Text

파일 Core 내부에는 `OcrDocumentResult.raw_text`와 `cleaned_text`가 존재한다. 그러나 `build_admin_ocr_response()`는 다음처럼 Clean만 노출한다.

```text
extractedText = result.cleaned_text
chunks = create_chunks(result.cleaned_text, ...)
```

`OcrDocumentResponse`에는 `raw_text` 필드가 없으므로 Job에 Raw가 남지 않는다. 저장 시에도 다음 값이 전달된다.

```text
admin_documents.ocr_extracted_text = job.result.extracted_text
                                      = result.cleaned_text
```

즉 현재 DB 컬럼 이름은 `ocr_extracted_text`이지만 실제 inline 저장 내용은 **최소 정제본**이다.

### 6.2 형식별 예시

PDF:

```text
## 페이지 1

# 소제목
본문...

[이미지 OCR]
도표 안의 Text...
```

DOCX:

```text
## DOCX 문서

# Heading 1
본문...

| 항목 | 내용 |
| --- | --- |
| ... | ... |

### 이미지 OCR 1
이미지 Text...
```

PPTX:

```text
## 슬라이드 1

제목
본문

### 발표자 노트
...

### 이미지 OCR 1
...
```

웹 URL:

```text
# HTML H1

## HTML H2

본문 문단...

## 웹페이지 이미지 OCR: 이미지 alt/title 또는 기본 label

이미지 OCR Text...
```

웹의 `<title>`은 `documentName`에는 사용되지만 본문 Text에 자동 삽입되지는 않는다. 페이지 안에 H1이 없으면 DB Chunk에는 문서 제목이 없을 수 있다.

### 6.3 제목·소제목·표·이미지 위치

| 항목 | 현재 상태 |
|---|---|
| 파일명/웹 title | Preview의 문서명에는 있음, DB 별도 컬럼에는 없음 |
| HTML heading | Markdown `#` 구조로 보존 |
| DOCX heading/list | Word Style 기반 Markdown 보존 |
| PDF heading | `pymupdf4llm` 결과에 따라 보존 |
| DOCX/PPTX table | Markdown Table로 변환 |
| HTML table | `itertext()`를 공백으로 합친 단순 Text이며 행/열 구조 손실 가능 |
| Hybrid PDF 이미지 | 원래 Block 순서에 삽입 |
| DOCX/PPTX 이미지 | 해당 문서/슬라이드 Text 뒤에 append |
| 웹 이미지 | 전체 HTML 본문 뒤에 append |
| OCR 출처 구분자 | PDF `[이미지 OCR]`, Office `### 이미지 OCR N`, 웹 `## 웹페이지 이미지 OCR: label` |

## 7. Text 정제 현황

현재 정제는 “RAG 품질 정제”가 아니라 **원문 의미를 바꾸지 않는 최소 정규화 + 일부 형식별 추출 정리** 수준이다.

### 7.1 공통 최소 정제

`ai/ocr/postprocessing.py::clean_document_text()`가 수행하는 항목은 다음뿐이다.

- CRLF를 LF로 통일
- Unicode NFKC 정규화
- 일부 제어문자 제거
- 줄 끝 Space 제거
- 3개 이상 연속 빈 줄을 2개로 축소
- 앞뒤 공백 제거

PaddleOCR 결과에는 추가로 다음이 적용된다.

- Confidence 기준 미달 Line을 Clean Text에서 제외
- 같은 페이지에서 연속으로 완전히 같은 OCR Line만 제거
- Box 좌표 기준 읽기 순서 정렬

### 7.2 정제 항목별 판정

| 정제 항목 | 현재 구현 | 구현 위치 | 문제점 | 추가 필요 |
|---|---|---|---|---|
| HTML `nav` 제거 | 완료 | `ai/ocr/extractors/web.py` | `<nav>` Tag에 한정 | 사이트별 보강 권장 |
| HTML `header` 제거 | 부분 구현 | 본문 후보 Marker 감점 | `<header>` 자체를 제거하지 않음 | 필요 |
| HTML `footer` 제거 | 완료 | DOM 제거 XPath | `footer` 외 class 기반 Footer는 후보 감점만 | 권장 |
| `script/style/noscript/template` 제거 | 완료 | DOM 제거 XPath | 동적 렌더링 본문은 수집하지 못함 | 현 범위 충분 |
| 메뉴/버튼 Text 제거 | 부분 구현 | 본문 후보 scoring, Block XPath | fallback `itertext()`에서는 섞일 수 있음 | 필요 |
| 공백 정규화 | 부분 구현 | `clean_document_text`, OCR `clean_text` | 일반 문서의 한 줄 중복 Space는 유지될 수 있음 | 권장 |
| 빈 줄 정리 | 완료 | `EXCESSIVE_BLANK_LINES` | 의미 단락 2줄은 유지 | 충분 |
| 중복 OCR Line 제거 | 부분 구현 | `dedupe_consecutive_lines` | 연속·동일 페이지·완전 일치만 제거 | 권장 |
| 중복 Line/문단 제거 | 미구현 | 없음 | Header/Footer 반복, 본문 재노출 유지 | 필요 |
| 깨진 문자 정리 | 부분 구현 | NFKC, 제어문자 제거 | Mojibake, `�`, 비정상 조합 처리 없음 | 권장 |
| OCR 특수문자 Noise 제거 | 미구현 | 없음 | 기호 위주 Chunk도 Admin 문자 Chunker에 들어감 | 필요 |
| 불필요 URL Text 제거 | 미구현 | 없음 | 본문에 노출된 링크/추적 Text 유지 | 권장 |
| HTML 본문과 이미지 OCR 중복 제거 | 미구현 | 없음 | alt/캡션/본문과 OCR 중복 가능 | 필요 |
| 메뉴·배너 이미지 OCR 차단 | 부분 구현 | decorative hint, 크기·용량 제한 | class/URL hint에 없는 배너는 OCR 가능 | 권장 |
| 제목/Section 보존 | 부분 완료 | HTML/Office/PDF Extractor | 웹 `<title>`은 본문 미포함 | 필요 |
| Table 의미 보존 | 형식별 상이 | Office/PDF | HTML Table 구조가 평탄화됨 | 권장 |

### 7.3 현재 발생 가능한 품질 문제

- 같은 의료 문장이 HTML 본문, 이미지 alt, 이미지 OCR에 중복될 수 있다.
- 웹페이지 이미지가 DOM 원래 위치가 아니라 문서 끝에 모여 Section 문맥이 끊긴다.
- 공공기관의 반복 Header, Breadcrumb, 관련 콘텐츠가 본문 후보 안에 있으면 남을 수 있다.
- PDF 페이지 Header/Footer가 페이지마다 반복되어 각 Chunk에 과대표집될 수 있다.
- OCR 오인식 기호가 Confidence를 통과하면 그대로 들어간다.
- 현재 Admin 문자 Chunker는 공통 `ai/rag.chunk_text()`의 garbage filter를 사용하지 않는다.

## 8. 정제 기능 추가 위치 분석

### 8.1 후보 비교

| 후보 | 장점 | 단점 | 현재 코드 적합성 |
|---|---|---|---|
| A. 추출 중 정제 | DOM, PDF Block 같은 형식 정보를 활용 가능 | 규칙이 각 Extractor로 분산되고 파일/URL 간 결과가 달라짐 | 형식 전용 정리에만 적합 |
| B. 추출 후 Raw 보존 → 공통 Cleaning → Chunk | 한 번의 규칙으로 Preview·저장·Embedding 일치, Raw 복구 가능, 테스트 쉬움 | Job 계약에 Raw/Clean을 함께 보유해야 함 | **최적** |
| C. Chunk 후 Chunk별 정제 | Chunk 단위 Noise 제거가 쉬움 | 정제 때문에 빈 Chunk/Index 불일치 발생, 문서 전체 중복 제거 불가, Embedding Preview와 어긋남 | 보조 검증 외 부적합 |

### 8.2 권장안

형식 의존 정리는 추출기에 유지하고, RAG 공통 정제는 **B 위치**에 둔다.

```text
Extractor
├─ HTML DOM 제거/본문 선택
├─ PDF Block 순서
├─ Office Heading/Table
└─ OCR Confidence
       ↓
raw_text 보존
       ↓
RAG Document Cleaning Service
       ↓
cleaned_text
       ↓
Preview → Chunk → Embedding → 저장
```

권장 책임은 다음과 같다.

```text
clean(raw_text, source_type, structural_hints)
→ cleaned_text
→ warnings
→ cleaning_version
```

파일명 후보는 `rag_document_cleaner.py` 또는 `document_cleaning_service.py`가 적절하다. OCR Core의 `clean_document_text()`는 저수준 손실 없는 정규화로 계속 재사용하고, RAG 품질 규칙은 별도 Service로 분리하는 것이 책임상 안전하다.

### 8.3 공통 Cleaning 최소 규칙

초기에는 재현 가능한 규칙만 포함한다.

1. Unicode/제어문자/줄 끝/빈 줄 정규화 재사용
2. 연속 중복 Line 제거
3. 반복 Header/Footer 후보 제거: 여러 Page/Section에서 일정 횟수 이상 반복될 때만
4. 완전 동일 또는 정규화 후 동일한 인접 문단 제거
5. 기호 비율이 과도하고 의미 문자 수가 매우 적은 Line 제거
6. 이미지 OCR Section 내 빈/짧은 Noise 제거
7. HTML 본문과 이미지 OCR의 정확 일치·높은 중복 문장 제거
8. Heading/페이지/슬라이드/이미지 OCR Marker는 보존

유사도 기반 공격적 문장 삭제나 LLM 재작성은 초기 기본 규칙에 넣지 않는 편이 안전하다. 의료 문장은 비슷해 보여도 조건·수치가 다를 수 있다.

## 9. 이미지 OCR Text 처리 현황과 권장안

### 9.1 현재 위치

| 입력 | 이미지 OCR 위치 |
|---|---|
| Hybrid PDF | Native Text Block 사이 원래 이미지 위치 |
| DOCX | 문서 본문 뒤, 이미지 순번별 append |
| PPTX | 슬라이드 Text 뒤, 이미지 순번별 append |
| 웹 URL | 전체 HTML 본문 뒤, 이미지 label별 append |
| PNG/JPG | 문서 전체 Text |

### 9.2 현재 중복 방지

- 웹 이미지 URL 중복은 제거한다.
- Office의 동일 binary 이미지 중복은 제거한다.
- decorative image hint와 최소 이미지 크기 기준이 있다.
- **Text 의미 중복은 제거하지 않는다.**

### 9.3 최소 권장 형식

현재 Markdown Marker 구조를 유지하되 label과 출처를 명확히 한다.

```text
## 이미지 OCR
- label: 혈압 분류표
- source: 문서 내 이미지 2

OCR Text...
```

다만 DB에 별도 이미지 테이블을 추가하는 것은 이번 규모에서 과하다. 최소 구현은 Text Marker와 문서 Metadata만으로 충분하다.

### 9.4 정제 정책

- HTML alt/캡션과 OCR이 완전히 같으면 OCR Section을 제거하거나 한 번만 남긴다.
- 64×64보다 크더라도 icon·logo·banner 성격이면 OCR 대상에서 제외한다.
- 의료 도표처럼 짧은 단어 나열만 있는 경우 무조건 버리지 말고 최소 의미 문자·숫자·단위 조합을 확인한다.
- Confidence가 낮거나 의미 문자 비율이 낮은 결과는 Preview에 경고하고 기본 저장 제외 후보로 표시한다.
- Vision LLM은 기본안에 포함하지 않는다.

## 10. Metadata 현황 및 최소 요구사항

### 10.1 현재 구현

현재 영구 저장되는 문서 수준 정보는 사실상 다음뿐이다.

```text
id
original_file_url
ocr_extracted_text(실제로는 Clean)
ocr_status
uploaded_by(NULL인 현재 흐름)
created_at
```

Job에는 `documentName`, `sourceType`, `sourceUrl`, 문서 유형 Notes가 있으나 DB 저장 시 대부분 유실된다.

공통 `ai.rag.RetrievedChunk`에는 `source`, `metadata` 필드가 있지만 `rag_search_service`는 값을 채우지 않는다. Frontend `api/rag.ts`도 `source`와 `metadata`를 기대하지만 Backend `RagSearchResultItem`에는 해당 필드가 없다. 즉 Metadata 계약은 **타입 흔적만 있고 저장·조회·응답은 미구현**이다.

### 10.2 Metadata 우선도

| Metadata | 우선도 | 생성 방식 | 저장 위치 | 이유 |
|---|---|---|---|---|
| `document_id` | 필수·기존 | DB UUID | `admin_documents.id` | 추적 기준 |
| `document_title` | 필수 | 파일명/HTML title 자동 + 사용자 수정 | 전용 컬럼 | 관리·출처 표시 |
| `source_url/reference` | 필수·기존 | 최종 URL 또는 file/R2 reference | `original_file_url` | 원본 추적 |
| `source_type` | 필수 | 입력 경로 자동 | 전용 컬럼 | URL/file/R2 구분 |
| `source_name` | 필수 | URL domain 후보 + 사용자 확인 | JSONB | 의료 출처 신뢰성 |
| `language` | 필수 | 기본 `ko`, 자동 감지 후보 + 사용자 확인 | JSONB | 다국어 확장·검증 |
| `license` | 필수 | 사용자/관리 파일 입력 | JSONB | 사용 가능 여부 추적 |
| `collected_at` | 필수·기존 대체 가능 | 저장 시각 | 우선 `created_at` 재사용 | 현재 규모 충분 |
| `category` | 권장 | 수동 선택/Rule 후보 | JSONB | 필터·평가 기반 |
| `topic` | 권장 | 수동/Rule 후보 | JSONB | 문서 탐색 품질 |
| `content_hash` | 권장 | Clean Text SHA-256 | 전용 컬럼 | 중복 탐지 |
| `symptoms` | 권장 | 수동 또는 검토된 후보 | JSONB | 향후 필터·평가 |
| `disease` | 후순위 | 검토된 구조화 | JSONB | 현재 검색은 사용하지 않음 |
| `department` | 후순위 | 검토된 구조화 | JSONB | 현재 질문 분류와 별도 책임 |
| `red_flag` | 후순위 | 전문가/검토된 Rule | JSONB | 오분류 위험이 큼 |
| `updated_at` | 후순위 | DB | 전용 컬럼 | 수정/재처리 기능 도입 시 |

`source_name`, `language`, `license`를 JSONB에 두더라도 저장 전 UI/API에서 필수 검증할 수 있다. 전용 컬럼이 없다는 뜻이 선택 입력이라는 뜻은 아니다.

### 10.3 현실적인 생성 방식

약 30개 문서 기준 권장 방식은 **혼합**이다.

```text
자동
├─ document_title 후보
├─ final source_url
├─ domain
├─ source_type
└─ language 후보

사용자 확인/입력
├─ source_name
├─ license
├─ category
└─ topic

선택적 Rule/LLM 후보
├─ symptoms
├─ disease
├─ department
└─ red_flag
       ↓
관리자 검토 후 저장
```

- LLM 구조화 결과를 검토 없이 저장하는 방식은 재현성과 의료 오분류 위험 때문에 기본안으로 부적합하다.
- Excel/CSV는 30개 자료의 초기 Metadata를 일괄 관리하는 선택 기능으로 유용하지만 Admin 수동 등록의 필수 의존성으로 만들 필요는 없다.
- URL/HTML 자동 추출은 후보 생성에만 사용하고 출처기관·라이선스는 관리자가 확정하는 것이 현실적이다.

## 11. Chunking 현황

### 11.1 현재 Admin Chunker

`backend/app/services/ocr_chunk_service.py`는 문자 수 기준이다.

```text
최대 chunk_size까지 전진
→ 뒤에서부터 \n\n, \n, '. ', Space 순으로 자연 경계 탐색
→ 최소 60% 이후 경계만 선택
→ 문자 overlap만큼 되돌아감
```

기본값은 512자, 10%인 50자 overlap이다. UI는 50~2048자와 0/10/15/20%를 제공한다.

### 11.2 별도 Token Chunker

`ai/rag/chunking.py`에는 다음 기능이 이미 있다.

- `cl100k_base` 근사 Token 수
- 기본 300 tokens, overlap 60 tokens
- 문장/빈 줄/조항 경계
- 거대 문장 강제 Token 분할
- 기호뿐인 garbage Text 제거

하지만 이 Chunker는 현재 Admin RAG 저장 경로에서 호출되지 않는다. 이를 호출하는 `document_ingestion_service.ingest_document()`도 Router/Service에서 미호출 상태다.

### 11.3 권장 판단

최소 구현에서는 **현재 Admin 문자 Chunker를 유지**한다.

이유:

- Preview와 저장 Chunk가 현재 완전히 일치한다.
- 이미 Jina/BGE 저장과 검색이 이 Chunk 기준으로 운영된다.
- 정제와 Metadata 작업에 Chunk 전략 변경을 묶으면 원인 분석이 어려워진다.
- 팀 설계의 500~800 tokens는 평가 후 확정할 값이다.

후속 평가에서 Token Chunker가 우수하면 `ai/rag.chunk_text()`를 그대로 가져오기보다 Admin 설정·Preview·대용량 Streaming·Provider token limit을 함께 맞춘 통합 작업으로 진행해야 한다.

## 12. Jina/BGE Embedding 현황

현재 실행 경로는 다음과 같다.

| 항목 | 상태 |
|---|---|
| Provider | `jina-v4`, `medical-bgem3` |
| 문서 입력 유형 | `passage` |
| 질문 입력 유형 | `query` |
| 실제 논리 차원 | 각 1024 |
| 물리 저장 폭 | `VECTOR(2048)`에 뒤쪽 0 Padding |
| 저장 단위 | Chunk당 Provider별 1행 |
| Unique | `(chunk_id, provider_name)` |
| 검색 | Provider 이름별 cosine distance |
| 결합 | UUID 기반 RRF, 기본 k=60 |

정제 후 Chunk 문자열을 기존 `embed_chunks()`에 전달하면 되므로 `chunk_embeddings` Schema나 Provider 구현은 변경할 필요가 없다.

### 12.1 검증

현재 저장 전 다음을 검사한다.

- 빈 Chunk 여부
- 두 Provider 존재 여부
- Provider별 Vector 수와 Chunk 수 일치
- 모든 Vector가 1024차원인지

Remote Provider는 응답 모델명, 개수, 차원, 유한값, 0 Vector 등을 추가 검증하고 단위 Vector로 정규화한다.

### 12.2 기존 Gemini 컬럼

`document_chunks.embedding VECTOR(1024)`은 레거시 Gemini용이다.

- 새 Admin 저장은 이 컬럼을 채우지 않는다.
- 새 검색/RRF도 이 컬럼을 읽지 않는다.
- 기존 데이터 호환 때문에 Schema에는 남아 있다.
- 이번 단계에서는 **유지하되 완전 미사용 레거시로 표시**하는 것이 맞다.
- 삭제는 데이터 확인과 별도 Migration 과제로 분리한다.

| `chunk_id` | UUID | 아니오 | FK → `document_chunks.id`, `ON DELETE CASCADE` | B-tree Index | 없음 | 사용 |
| `provider_name` | VARCHAR(100) | 아니오 | - | Index, `(chunk_id, provider_name)` Unique | 없음 | 사용 |
| `dimension` | INTEGER | 아니오 | - | 없음 | 없음 | 실제 1024 기록 |
| `embedding` | VECTOR(2048) | Migration상 아니오 | - | ANN Index 없음 | 없음 | 0 Padding Vector 저장 |
| `created_at` | TIMESTAMPTZ | 예 | - | 없음 | `now()` | 사용 |

ORM의 `ChunkEmbeddings.embedding`은 `Optional[Any]`이고 `nullable=False`가 명시되지 않아 Model Metadata와 Migration의 NOT NULL 계약이 어긋난다. 실제 DB는 2026-09-01 흐름 문서에서 정상 Vector 저장이 확인됐지만, 정확한 물리 Nullable은 실 DB 확인이 필요하다.

### 13.4 Migration 재현성 문제

초기 Migration `5d7e62474617_create_tables.py`의 `upgrade()`가 빈 `pass`다. 현재 Migration 체인은 기존 기본 테이블을 새 DB에 처음부터 재현하지 못한다. `chunk_embeddings` 추가 Migration은 존재하지만 부모 `admin_documents`, `document_chunks` 생성 SQL은 Migration에 없다.

이번 정제 기능만의 문제는 아니지만 새 Metadata Migration을 만들기 전에 반드시 기준 Schema 재현 전략을 확인해야 한다.

## 15. 최소 DB 변경안

### 15.1 제안

`vector_db.admin_documents`만 확장한다.

```text
document_title  VARCHAR(255) NULL
source_type     VARCHAR(30)  NULL
cleaned_text    TEXT         NULL
metadata        JSONB        NULL 또는 '{}' 기본값
content_hash    VARCHAR(64)  NULL  [권장]
```

기존 행과 무중단 호환을 위해 최초 Migration에서는 Nullable로 추가한다. 새 저장 API에서 값 입력을 강제하고 기존 데이터 Backfill 후 필요하면 NOT NULL로 강화한다.

물리 컬럼명 `metadata`를 쓸 경우 ORM에서는 다음 원칙이 필요하다.

```text
DB column: metadata
ORM attribute: document_metadata
```

### 15.2 Raw/Clean 저장 의미

새 행의 의미는 다음으로 고정한다.

```text
ocr_extracted_text = 정제 전 추출 Raw Text
cleaned_text        = Chunk/Embedding에 사용한 최종 Clean Text
document_chunks     = cleaned_text를 분할한 결과
```

기존 행은 `ocr_extracted_text`에 Clean Text가 들어 있으므로 다음처럼 호환한다.

- 기존 행의 `cleaned_text`는 NULL 허용
- 조회 시 `COALESCE(cleaned_text, ocr_extracted_text)` 사용 가능
- 기존 `document_chunks`와 Embedding은 그대로 검색
- 기존 행 전체 재임베딩은 Migration 자체에 필요하지 않음

### 15.3 대용량 문서 예외

대용량 원본 전체를 `ocr_extracted_text`에 다시 복제하면 Streaming 설계의 목적이 약해진다. 최소 프로젝트 범위에서는 다음 중 하나를 명시적으로 선택해야 한다.

1. 30개 의료 문서는 20MB 이하만 정제·Metadata 정식 지원하고, 대용량 경로는 기존 Preview 의미 유지
2. 대용량은 `original_file_url`의 R2 Object를 Raw 원본으로 간주하고 DB Text 컬럼에는 Preview만 저장

두 경우 모두 Metadata에 `text_storage_mode: inline|r2`, `text_truncated: true|false`를 기록해야 오해를 막을 수 있다. 이번 일정에는 2번이 현실적이다.

### 15.4 장단점

| 장점 | 단점 |
|---|---|
| 테이블 1개만 변경 | Raw/Clean Text 중복 저장 |
| 기존 Chunk/Embedding/RRF 무변경 | Metadata 일부가 JSONB라 DB 타입 강제가 약함 |
| 기존 행 Nullable 호환 | 대용량 문서 의미를 별도 표시해야 함 |
| 향후 Metadata 확장 용이 | 정제 Revision 이력은 남기지 못함 |

## 17. 저장 API와 Transaction 분석

### 17.1 현재 Payload

```json
{
  "jobId": "완료된 Job ID"
}
```

이 계약은 좋은 구조다. Frontend가 Raw Text, Clean Text, Chunk, Vector 전체를 다시 보내지 않는다.

### 17.2 Metadata 추가 시 권장 Payload

Frontend가 보내야 하는 값:

```text
jobId
사용자가 확인/수정한 최소 Metadata
선택한 저장 정책 또는 중복 확인 값
```

Backend Job이 보유해야 하는 값:

```text
raw_text
cleaned_text
source_type
source_url/reference
자동 추출 title/domain/language 후보
chunks
chunk_config
cleaning_version
```

Vector는 항상 Backend가 생성한다. Frontend가 Clean 전체 Text를 다시 보내는 방식도 피한다. 사용자가 Clean Preview를 편집하는 기능까지 필요해질 때만 수정본을 Job 상태에 저장하는 별도 API를 둔다.

### 17.3 정제와 Transaction

정제는 DB Transaction 전에 완료하는 것이 맞다.

```text
Extraction
→ Cleaning
→ Metadata validation
→ Chunk
→ Embedding
→ DB Transaction
```

정제 실패는 DB 쓰기 전에 종료하고, 성공한 Clean/Chunk/Embedding만 함께 저장한다.

### 17.4 Transaction 유지 가능성

- inline 파일·URL: Metadata 컬럼을 부모 `AdminDocuments` 생성자에 추가하면 기존 단일 Transaction 유지 가능
- 대용량: 현재 다중 Commit 구조 유지 가능하나 “완전한 단일 Transaction”은 아님

대용량 경로는 `ocr_status='processing'`인 문서를 검색에서 제외하고 실패 시 Cascade 삭제하는 방식으로 논리적 원자성을 보완한다. 정제·Metadata 추가를 이유로 이 경로까지 전면 재작성할 필요는 없다.

## 18. 중복 등록과 기존 데이터 호환성

### 18.1 현재 중복 정책

현재 저장은 항상 새 `admin_documents` 행을 INSERT한다.

- URL Upsert 없음
- 파일 Hash 없음
- Clean Text Hash 없음
- 동일 Job의 저장 재호출 방지용 영구 상태 없음
- `(document_id, chunk_index)` Unique 없음

Frontend는 성공 후 같은 화면의 Save 버튼을 막지만 API 재호출이나 다른 Job 재등록은 막지 못한다.

### 18.2 최소 정책

```text
canonical source reference
+
SHA-256(cleaned_text)
```

권장 동작:

1. 동일 `content_hash`가 이미 있으면 기본 저장을 막고 기존 문서 ID를 안내
2. 같은 URL이지만 Hash가 다르면 “내용 변경 가능” 경고
3. 의도적 새 Version은 초기에는 자동 허용하지 않고 관리자 확인 후 별도 정책으로 처리
4. URL의 tracking query는 canonicalization 후보이나 기능성 query까지 지우지 않도록 보수적으로 적용

`content_hash`에 즉시 Global Unique를 걸면 의도적으로 같은 본문을 다른 출처로 보존하는 경우까지 막을 수 있다. 초기에는 Index + Service 검사 + 명시적 관리자 확인이 안전하다.

### 18.3 기존 데이터

현재 DB에는 다음이 섞일 수 있다.

```text
기존 Gemini Vector가 document_chunks.embedding에 있는 문서
Text/Chunk만 있고 chunk_embeddings가 없는 문서
새 Jina/BGE chunk_embeddings가 있는 문서
```

영향:

- 새 Nullable 문서 컬럼 추가는 기존 행을 깨지 않는다.
- 기존 Chunk/Embedding은 재임베딩 없이 계속 현재 검색 조건대로 동작한다.
- `chunk_embeddings`가 없는 기존 문서는 현재 Jina/BGE 검색에 나타나지 않는다.
- 기존 `ocr_extracted_text`는 Clean인지 Raw인지 행별로 구분할 수 없으므로 일괄 Raw로 재해석하면 안 된다.
- 기존 행 Metadata Backfill은 파일 reference/URL/과거 문서 기록으로 별도 수행해야 한다.

### 21.4 통합 기준

서로 다른 적재 구현 중 **현재 Admin 실제 호출 경로**를 기준으로 통합하는 것이 가장 안전하다.

```text
기준:
admin_ocr.save_ocr_result_with_embeddings()
→ embedding_service
→ DocumentRepository.save_with_chunks()

비기준:
document_ingestion_service.ingest_document()
```

이유:

- 기준 경로는 Frontend Job/Preview와 연결돼 있다.
- Jina/BGE 이중 저장과 Transaction 테스트가 있다.
- 저장한 Chunk가 즉시 현재 RRF 검색 대상이 된다.
- 별도 ingestion은 호출되지 않고 문자/Token Chunk가 달라 결과가 이중화될 수 있다.
- 별도 ingestion은 Chunk 생성과 Provider별 Embedding을 여러 Commit으로 저장해 실패 시 부분 상태가 생길 수 있다.

재사용 대상은 별도 ingestion 함수 자체가 아니라 그 아래의 순수 Token Chunker·Provider 계약·검색/RRF 구성요소다.

## 27. 필수 질문 답변

### Q1. 현재 RAG 탭에서 최종적으로 Chunk에 전달되는 Text는 정확히 어떤 형태인가?

`OcrDocumentResult.cleaned_text`다. 파일별 구조 Marker와 Confidence를 통과한 OCR Text에 NFKC·제어문자·빈 줄 최소 정리를 적용한 문자열이다. `raw_text`는 Chunk에 전달되지 않는다.

### Q2. 웹 본문 Text와 이미지 OCR Text는 현재 어디서, 어떻게 합쳐지는가?

`ai/ocr/extractors/web.py::build_web_ocr_result()`에서 HTML 본문을 첫 Section으로 두고, 내부 이미지 OCR을 `## 웹페이지 이미지 OCR: {label}` Section으로 문서 끝에 차례대로 append한다. 원래 DOM 이미지 위치에는 삽입하지 않는다.

### Q3. 현재 Text 정제 기능은 어느 수준까지 구현되어 있는가?

최소 정규화와 형식별 추출 정리 수준이다. Unicode/제어문자/빈 줄, OCR Confidence·연속 동일 Line, HTML의 일부 불필요 Tag 제거는 구현돼 있다. 문단 중복, 반복 Header/Footer, OCR Noise, 본문/이미지 OCR 의미 중복, URL Noise는 미구현이다.

### Q4. RAG용 정제를 추가한다면 어느 Service/단계가 가장 적절한가?

형식별 Extractor 이후, Raw 보존 뒤, Preview/Chunk 이전의 독립 `RAG Document Cleaning Service`가 가장 적절하다.

### Q5. 정제 전 Raw Text와 정제 후 Clean Text를 둘 다 저장해야 하는가?

20MB 이하 공식 의료 문서에는 둘 다 저장하는 것이 맞다. `ocr_extracted_text=Raw`, 새 `cleaned_text=Embedding 입력`으로 의미를 고정한다. 기존 행은 Nullable 호환한다. 대용량은 R2 원본을 Raw로 간주하고 DB에는 Preview/모드를 명시하는 예외가 현실적이다.

### Q6. 약 30개 의료 문서 기준 필요한 최소 Metadata는 무엇인가?

문서 ID, 제목, 원본 URL/reference, source type, source name, language, license, 저장 시각이다. category/topic은 권장한다. symptoms/disease/department/red_flag는 검토 체계가 준비된 뒤 추가한다.

### Q7. Metadata 입력/생성 방식은 무엇이 현실적인가?

혼합 방식이다. URL/title/domain/source type은 자동 후보, source name/license/category/topic은 관리자 확인·입력, 의료 분류는 Rule/LLM 후보를 만들더라도 관리자 검토 후 저장한다. CSV는 30개 초기 일괄 관리의 선택 기능이다.

### Q8. 현재 Neon Schema로 정제된 RAG 문서를 충분히 저장할 수 있는가?

정제 Chunk와 Vector 자체는 저장할 수 있다. 그러나 Raw/Clean 분리와 최소 Metadata를 구조적으로 보존할 수 없어 목표 전체에는 부족하다.

### Q9. DB 변경이 필요하다면 정확히 어떤 Table/Column을 최소 수정해야 하는가?

`vector_db.admin_documents`에 `document_title`, `source_type`, `cleaned_text`, `metadata JSONB`가 필요하다. `content_hash`는 중복 방지를 위해 권장한다. 기존 행 호환을 위해 최초에는 Nullable이 안전하다.

### Q10. 현재 `document_chunks`, `chunk_embeddings`, Jina/BGE 저장 구조는 그대로 재사용 가능한가?

가능하다. 최소안에서는 Schema 변경이 필요 없다. Clean Text를 먼저 만든 뒤 현재 Chunker 결과를 같은 Jina/BGE와 Repository에 전달하면 된다.

### Q11. 기존 RRF 검색에 DB 변경이 영향을 주는가?

부모 문서에 Nullable 컬럼을 추가하는 것만으로는 영향이 없다. `document_chunks`와 `chunk_embeddings` 및 provider name을 유지하면 RRF는 그대로 동작한다. Metadata 반환을 위해 Parent Join을 추가할 때 회귀 Test가 필요하다.

### Q12. Hugging Face Dataset이 현재 단계에서 실제로 필요한가?

불필요하다. 30개 수동 등록에는 Cleaning Version, JSONB Metadata, Hash와 평가 Dataset이면 충분하다. 대량 Batch·팀 공유·Snapshot이 필요해질 때 선택 도입한다.

### Q13. 이 기능은 현재 프로젝트 구조에서 어느 정도 작업량으로 구현 가능한가?

중간 규모다. 최소 구현 4~7 개발일, 중복·Backfill까지 6~10 개발일 정도로 본다. Token Chunk 전환과 Revision/대용량 완전 지원은 별도 과제다.

### Q14. 최소 구현 범위만 잡는다면 정확히 무엇만 추가하면 되는가?

공통 Cleaner, Raw/Clean Job 계약, Clean Preview, 최소 Metadata UI/API, `admin_documents` 최소 컬럼, Hash 중복 경고, 저장/검색 회귀 Test만 추가한다. Chunk/Jina/BGE/RRF는 재사용한다.

### Q15. 다른 팀원이 구현한 RAG 관련 기능은 무엇인가?

공통 OCR, Token Chunker, Provider 추상화, `chunk_embeddings`, DB 검색, RRF, Search UI, Chat Context, 진료과 분류, Red Flag 감지, 검색 평가가 있다. 상세 위치·사용 여부·Git 근거는 21절에 정리했다. `document_ingestion_service`는 구현됐지만 현재 호출되지 않는다.

### Q16. 새로 만들지 않고 재사용할 부분은 정확히 무엇인가?

입력 UI와 Job, 파일/웹/OCR Extractor, 최소 Unicode 정규화, 문자 Chunker, Jina/BGE Provider, 3단 저장 Repository, pgvector 검색, RRF, 상담 Context, 검색 평가 기반을 재사용한다. 새로 필요한 것은 RAG Cleaner와 Metadata 연결 계층이다.

### Q17. 서로 다른 RAG 구현이 중복된다면 어느 구현을 기준으로 통합하는 것이 안전한가?

현재 실제 호출되는 `admin_ocr → embedding_service → DocumentRepository`를 기준으로 한다. 미연결 `document_ingestion_service`는 통째로 연결하지 않는다. 필요하면 그 아래 `ai/rag` Token Chunker 같은 순수 기능만 평가 후 가져온다.

## 28. 최종 결론

현재 프로젝트는 이미 RAG 저장·검색의 어려운 부분을 대부분 갖고 있다.

```text
현재 추출 기능
+
작은 공통 정제 단계
+
문서 단위 최소 Metadata
+
현재 문자 Chunk
+
현재 Jina/BGE
+
현재 Neon 3단 저장
+
현재 RRF/Chat
```

이 방향이 가장 안전하다.

핵심 결정은 다음과 같다.

1. 정제는 Extractor와 Chunk 사이의 독립 Service로 둔다.
2. Raw와 Clean을 모두 보존하되 기존 행과 대용량 경로는 호환 예외를 둔다.
3. Metadata는 문서 단위 JSONB 중심으로 저장하고 Chunk마다 복제하지 않는다.
4. `admin_documents`만 최소 확장하고 `document_chunks`, `chunk_embeddings`는 유지한다.
5. 현재 실제 Admin 저장 경로를 통합 기준으로 삼고 미연결 ingestion을 중복 연결하지 않는다.
6. Hugging Face, Revision 테이블, Token Chunk 전환, 의료 자동 분류는 후순위로 분리한다.
7. 구현 전 빈 초기 Migration과 실제 DB 기준 Schema를 먼저 확인한다.

후속 구현은 별도 코딩 허가 후 진행해야 한다.
